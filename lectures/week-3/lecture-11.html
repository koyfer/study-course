CI/CD і Jenkins: конвеєр збирання, Jenkinsfile і Pipeline as Code

CI-сервер — це «конвеєр» команди: на кожну зміну в Git він сам збирає проєкт, проганяє тести й повідомляє про результат. Jenkins — найпоширеніший open-source CI-сервер, а Jenkinsfile описує конвеєр як код.

Чого ви навчитесь#

  • Пояснити, що таке Continuous Integration і з чого складається CI/CD-конвеєр.
  • Описати архітектуру CI-сервера: VCS, тригер, агенти збирання, артефакти, деплой.
  • Встановити Jenkins і знати його ключові налаштування.
  • Прочитати і написати declarative Jenkinsfile: agent, stages, steps, post, parameters, when.
  • Порівняти declarative і scripted pipeline та знати допоміжні інструменти Jenkins.
  • Пояснити архітектуру Jenkins: контролер, агенти, executors, мітки, workspace; типи задач і статуси збірки.
  • Безпечно працювати з секретами (Credentials, withCredentials, sshagent) і знати правила безпеки Jenkins.
  • Написати повний конвеєр: тести з junit, збірка і публікація Docker-образу, деплой зі схваленням; знати вбудовані змінні.
  • Порівняти Jenkins з GitHub Actions, GitLab CI, TeamCity та іншими системами.
  • Писати declarative pipeline з options, parameters, triggers, when, post, matrix і безпечною роботою з credentials.
  • Розгорнути Jenkins у Docker, налаштувати webhook, розуміти статуси збірки і читати консоль; порівнювати CI-системи.

Continuous Integration#

Визначення

Continuous Integration (CI) — практика, коли розробники часто (щонайменше щодня) інтегрують зміни в спільну гілку, а кожна інтеграція перевіряється автоматичним збиранням і тестами. Мета — знаходити помилки інтеграції якнайраніше (класичний опис — стаття Мартіна Фаулера «Continuous Integration»).

Далі по конвеєру — Continuous Delivery (кожна вдала збірка готова до релізу, вихід у production — після ручного схвалення) і Continuous Deployment (повністю автоматично). Різницю ми розібрали в лекції 1.

Jenkins#

Що це

Open-source CI/CD-сервер з вебінтерфейсом. Написаний на Java, працює в servlet-контейнері. Наступник (форк) Hudson.

Факти зі слайдів

Перший реліз — 2005 (як Hudson), ліцензія MIT, активна незалежна спільнота, 1500+ плагінів.

Jenkins 2.0 (2016)

Pipeline — «громадянин першого класу»: Pipeline as Code (Jenkinsfile) і новий інтерфейс Blue Ocean.

Встановлення (CentOS, як на лекції)

java -version                               # Jenkins потребує Java
wget -O /etc/yum.repos.d/jenkins.repo http://jenkins-ci.org/redhat/jenkins.repo
rpm --import http://pkg.jenkins-ci.org/redhat/jenkins-ci.org.key
yum install jenkins
service jenkins start                       # далі http://server:8080

Налаштування сервісу — /etc/sysconfig/jenkins: JENKINS_HOME="/var/lib/jenkins" (усі задачі, плагіни, історія), JENKINS_USER="jenkins", JENKINS_PORT="8080". Після першого входу: оновити/встановити плагіни, налаштувати Maven (для Java-проєктів), Git-плагін, і SSH-ключ для доступу до репозиторію (ssh-keygen → публічний ключ у GitHub, як у лекції 2). Адреси репозиторіїв Jenkins з часом змінювались — актуальну інструкцію беріть на jenkins.io.

Архітектура Jenkins: контролер, агенти, задачі, облікові дані#

ПоняттяЗначення
Controller (колишній master)центральний сервер: UI, планування, конфігурація, плагіни, облікові дані, історія збірок
Agent (node, slave)машина або контейнер, де виконуються збірки. Підключається по SSH (контролер ходить на агента) або inbound (агент сам підключається до контролера)

Типи задач і статуси збірки

  • Freestyle — налаштування мишкою у вебформі (старий підхід, не версіонується).
  • Pipeline — конвеєр з Jenkinsfile.
  • Multibranch Pipeline — окрема задача для кожної гілки і PR репозиторію з Jenkinsfile.
  • Folder / Organization Folder — групування і автоматичне сканування організації GitHub.
СтатусКолірЗначення
SUCCESSзелений (синій у старому UI)усі кроки пройшли
UNSTABLEжовтийзбірка є, але частина тестів впала (наприклад, junit знайшов провалені тести)
FAILUREчервонийкрок завершився помилкою (ненульовий код sh, помилка компіляції)
ABORTEDсірийзупинено вручну або за тайм-аутом
NOT_BUILTсірийетап пропущено (наприклад, умова when не виконалась)

Облікові дані (Credentials)

Секрети зберігаються в Jenkins зашифровано і підставляються в збірку за ID, а в лозі маскуються як ****. Типи: Username with password, Secret text (токен), SSH Username with private key, Secret file, Certificate.

withCredentials([usernamePassword(credentialsId: 'dockerhub',
                                  usernameVariable: 'DOCKER_USER',
                                  passwordVariable: 'DOCKER_PASS')]) {
    sh 'echo "$DOCKER_PASS" | docker login -u "$DOCKER_USER" --password-stdin'
}
sshagent(['deploy-key']) {
    sh 'ssh -o StrictHostKeyChecking=no deploy@10.0.1.10 "sudo systemctl restart app"'
}

Зверніть увагу на одинарні лапки в sh '...': змінну розкриє shell, а не Groovy, тож секрет не потрапить у текст команди, що логується. У подвійних лапках Groovy підставив би значення сам.

Безпека і супровід

  • Не запускати збірки на контролері (кількість executors контролера = 0): код зі збірки міг би прочитати всі секрети JENKINS_HOME.
  • Авторизація за ролями (Matrix/Role-based), вхід через SSO, регулярні оновлення Jenkins і плагінів (більшість вразливостей — у плагінах).
  • Бекап JENKINS_HOME (задачі, конфігурація, облікові дані); краще — Configuration as Code (плагін JCasC): уся конфігурація Jenkins у YAML-файлі в Git.
  • Швидкий старт у Docker: docker run -d -p 8080:8080 -p 50000:50000 -v jenkins_home:/var/jenkins_home jenkins/jenkins:lts (50000 — порт для inbound-агентів); початковий пароль — у docker logs або файлі secrets/initialAdminPassword.

Jenkinsfile: Pipeline as Code#

Jenkinsfile — опис конвеєра на Groovy DSL, що лежить у репозиторії поруч із кодом. Переваги зберігання в SCM: рев'ю й ітерації коду конвеєра, журнал змін (audit trail), єдине джерело правди.

Declarative (з 2017)

  • Декларативна модель, простіший і «суворіший» синтаксис
  • Валідація і візуальний редактор
  • Обмежує можливості — ідеально для типових CD-конвеєрів

Scripted

  • Імперативна модель — повноцінна мова програмування
  • Максимальна гнучкість, майже без обмежень
  • Для досвідчених користувачів і складних вимог

Спільне: обидва на Groovy, той самий Pipeline-движок, переважно однакові кроки, обидва вміють Shared Libraries і змішуються через крок script.

Приклад declarative Jenkinsfile

Зібрано з фрагментів слайдів (settings, stages, parameters, approval, post):

pipeline {
    agent any
    triggers { pollSCM('H/5 * * * *') }                // перевіряти репозиторій кожні 5 хв
    options {
        timeout(time: 60, unit: 'MINUTES')
        buildDiscarder(logRotator(numToKeepStr: '30'))  // зберігати 30 останніх збірок
    }
    parameters {
        string(name: 'DEPLOY_ENV', defaultValue: 'TESTING', description: 'The target environment')
    }
    environment {
        AWS_ACCESS_KEY_ID = credentials('my-aws-key')      // секрет із Jenkins Credentials
    }
    stages {
        stage('Build & unit tests') {
            steps {
                checkout scm
                sh './gradlew build'
                stash name: 'my-workspace', includes: 'build/**'
            }
        }
        stage('Acceptance tests') {
            parallel {                                       // гілки виконуються одночасно
                stage('Firefox') { steps { echo 'testing Firefox' } }
                stage('Chrome')  { steps { echo 'testing Chrome' } }
            }
        }
        stage('Deploy to Stage') {
            when { branch 'master' }                          // лише для master
            steps {
                timeout(time: 30, unit: 'DAYS') {
                    input message: 'Deploy to Stage?', submitter: 'admin,pete.pm'
                }
                unstash 'my-workspace'
                sh "echo deploying build ${env.BUILD_NUMBER} to ${params.DEPLOY_ENV}"
            }
        }
    }
    post {
        failure {
            emailext subject: "FAILED: ${env.JOB_NAME} [${env.BUILD_NUMBER}]",
                     body: "Check console output at ${env.BUILD_URL}",
                     recipientProviders: [culprits()]
        }
    }
}
ЕлементЩо робить
agentДе виконувати: any, мітка вузла, Docker-контейнер; agent none на верхньому рівні — не блокувати executor, поки чекаємо схвалення
sh / batВиконати команду в shell (*nix) / cmd (Windows)
git, checkout scmОтримати код з репозиторію
readFile, writeFile, fileExistsРобота з файлами в workspace
stash / unstashПередати файли між етапами, що виконуються на різних агентах
parallelПаралельне виконання етапів (з declarative 1.2)
inputРучне схвалення (approval) — людина натискає «Proceed»
whenУмова виконання етапу (гілка, змінна, вираз)
postДії після збірки: always, success, failure, unstable, changed…
script { }Вставка scripted-коду в declarative — «аварійний люк»; великий код виносять у Shared Library

Змінні Jenkins доступні як $BUILD_NUMBER у shell або env.BUILD_NUMBER у Groovy; параметри — params.ІМ'Я.

Scripted pipeline

node {                                     // виділити executor («важкий»)
    stage('Example') {
        if (env.BRANCH_NAME == 'master') {
            echo 'I only execute on the master branch'
        } else {
            echo 'I execute elsewhere'
        }
        try { sh 'exit 1' }
        catch (exc) { echo 'Something failed!'; throw exc }
    }
}

Крок node займає слот виконавця (можна фільтрувати за мітками: node('php7')); код поза node виконується «легким» виконавцем на master. Виконання конвеєра переживає перезапуск Jenkins.

Довідник declarative pipeline: усі секції з прикладами#

pipeline {
  agent …            ← ДЕ виконувати (обов'язково)
  environment { … }  ← змінні оточення і секрети
  options { … }      ← налаштування запуску: таймаут, ретраї, ротація збірок
  parameters { … }   ← параметри, які вводять при ручному запуску
  triggers { … }     ← КОЛИ запускати автоматично
  tools { … }        ← встановлені в Jenkins інструменти (JDK, Maven, Node)
  stages {           ← ЩО робити (обов'язково)
    stage('…') {
      when { … }     ← умова виконання етапу
      steps { … }    ← конкретні кроки (обов'язково в stage, якщо немає parallel/stages)
      post { … }     ← дії після етапу
    }
  }
  post { … }         ← дії після всього конвеєра
}

agent noneна рівні pipeline — агента немає; кожен stage задає свій

options — найкорисніші

options {
    timeout(time: 30, unit: 'MINUTES')            // зупинити «завислу» збірку
    retry(2)                                      // повторити весь pipeline до 2 разів при помилці
    buildDiscarder(logRotator(numToKeepStr: '20'))// тримати 20 останніх збірок — економія диска
    disableConcurrentBuilds()                     // не запускати дві збірки одного job паралельно
    timestamps()                                  // час у кожному рядку консолі
    skipDefaultCheckout()                         // не робити автоматичний checkout scm
}

parameters — запуск «Build with Parameters»

parameters {
    string(name: 'VERSION', defaultValue: '1.0.0', description: 'Тег образу')
    choice(name: 'ENV', choices: ['staging', 'production'], description: 'Куди розгортати')
    booleanParam(name: 'RUN_E2E', defaultValue: true, description: 'Запускати E2E-тести')
    password(name: 'TOKEN', defaultValue: '', description: 'Тимчасовий токен')
}
// у кроках: params.ENV, params.RUN_E2E; у shell — $ENV

triggers і синтаксис cron у Jenkins

triggers {
    pollSCM('H/5 * * * *')        // раз на ~5 хв перевіряти репозиторій; збірка — лише якщо є нові коміти
    cron('H 2 * * 1-5')           // щобудня близько 02:xx — нічна збірка незалежно від змін
    upstream(upstreamProjects: 'shop-lib', threshold: hudson.model.Result.SUCCESS)  // після успіху іншого job
}

Поля cron: хвилина, година, день місяця, місяць, день тижня — як у Linux. Особливість Jenkins — символ H (hash): Jenkins підставляє фіксоване для цього job, але «випадкове» значення. H 2 * * * для одного job означає 02:17, для іншого — 02:43. Так сотні нічних збірок не стартують одночасно рівно о 02:00. Найкращий тригер для CI — не опитування, а webhook: GitHub сам повідомляє Jenkins про push.

Jenkins маскує значення секретів у консолі (****), але лише точні збіги. Не виводьте секрети через echo і не передавайте їх у Groovy-рядки з подвійними лапками ("…${TOKEN}…") — Groovy підставить значення ще до shell. Правильно: одинарні лапки sh 'curl -H "Authorization: Bearer $TOKEN" …', тоді змінну розкриває shell.

Повний конвеєр: тести → Docker-образ → реєстр → деплой#

pipeline {
    agent { label 'docker' }
    environment {
        IMAGE = "ghcr.io/anna/shop-api"
        TAG   = "${env.BUILD_NUMBER}-${env.GIT_COMMIT.take(7)}"   // напр. 42-a1b2c3d
    }
    options {
        timeout(time: 30, unit: 'MINUTES')
        disableConcurrentBuilds()
        buildDiscarder(logRotator(numToKeepStr: '20'))
    }
    triggers { githubPush() }                    // webhook від GitHub

    stages {
        stage('Test') {
            agent { docker { image 'python:3.12-slim'; reuseNode true } }
            steps {
                sh 'pip install -r requirements.txt'
                sh 'pytest --junitxml=reports/junit.xml'
            }
            post { always { junit 'reports/junit.xml' } }   // графік тестів у UI, UNSTABLE при падіннях
        }
        stage('Build image') {
            steps { sh 'docker build -t $IMAGE:$TAG .' }
        }
        stage('Push image') {
            when { branch 'main' }
            steps {
                withCredentials([usernamePassword(credentialsId: 'ghcr',
                        usernameVariable: 'U', passwordVariable: 'P')]) {
                    sh 'echo "$P" | docker login ghcr.io -u "$U" --password-stdin'
                    sh 'docker push $IMAGE:$TAG'
                }
            }
        }
        stage('Deploy to staging') {
            when { branch 'main' }
            steps {
                sshagent(['staging-key']) {
                    sh 'ssh deploy@staging.local "docker pull $IMAGE:$TAG && docker rm -f api || true && docker run -d --name api -p 80:8000 $IMAGE:$TAG"'
                }
            }
        }
        stage('Deploy to production') {
            when { branch 'main' }
            steps {
                input message: "Deploy ${TAG} to production?", submitter: 'release-managers'
                sh 'kubectl set image deploy/api api=$IMAGE:$TAG'     // Continuous Delivery: реліз після схвалення людиною
            }
        }
    }
    post {
        success { echo "OK: ${env.BUILD_URL}" }
        failure { echo "FAILED: ${env.JOB_NAME} #${env.BUILD_NUMBER}" }   // тут — Slack/email
        always  { sh 'docker image prune -f || true' }
    }
}

Список з описами — на сторінці http://jenkins:8080/env-vars.html. Тег образу з номером збірки і хешем коміту однозначно пов'язує образ у реєстрі з кодом і збіркою, на відміну від latest.

Jenkins від установки до першого конвеєра з webhook#

Найшвидший старт — Jenkins у Docker

docker run -d --name jenkins -p 8080:8080 -p 50000:50000 \
  -v jenkins_home:/var/jenkins_home --restart unless-stopped jenkins/jenkins:lts
docker exec jenkins cat /var/jenkins_home/secrets/initialAdminPassword   # пароль першого входу
  1. Відкрити http://localhost:8080, ввести initial admin password.
  2. Обрати «Install suggested plugins» (Git, Pipeline, Credentials тощо).
  3. Створити адміністратора; вимкнути вхід без пароля.
  4. Порт 8080 — вебінтерфейс, порт 50000 — підключення агентів (JNLP/inbound).
  5. Том jenkins_home містить усе: конфігурацію, задачі, історію збірок, плагіни, облікові дані. Його і бекаплять.

Типи задач (jobs)

ТипЯк налаштовуєтьсяКоли
Freestyle projectгалочки у вебінтерфейсі: репозиторій, тригер, кроки shellпрості разові задачі; не під контролем версій — для серйозних конвеєрів не рекомендують
PipelineJenkinsfile в репозиторії (або вставлений у налаштування job)один конвеєр для однієї гілки
Multibranch PipelineJenkins сканує репозиторій і створює job для кожної гілки і PR, де є Jenkinsfileосновний вибір для командної роботи: кожен PR перевіряється автоматично
Organization Folderсканує всю організацію GitHub/Bitbucket і створює multibranch для кожного репозиторіюбагато репозиторіїв з однаковим підходом

Webhook: GitHub повідомляє Jenkins про push

  1. У Jenkins: плагін GitHub встановлено; у job увімкнено GitHub hook trigger for GITScm polling (у Jenkinsfile — triggers { githubPush() }).
  2. У GitHub: репозиторій → Settings → Webhooks → Add webhook.
  3. Payload URL: https://jenkins.example.com/github-webhook/ (зі слешем у кінці), Content type: application/json, подія — Just the push event (для multibranch — також Pull requests).
  4. Jenkins має бути доступний з інтернету (або через проксі чи тунель). У Recent Deliveries видно відповідь Jenkins: 200 — гаразд.

Перевага над pollSCM: збірка стартує за секунди після push, і Jenkins не опитує репозиторій сотні разів на день даремно.

СтатусКолірТипова причина

Артефакти, звіти тестів і спільні бібліотеки

post {
    always {
        junit 'reports/**/*.xml'                               // графік тестів, UNSTABLE при падіннях
        archiveArtifacts artifacts: 'dist/*.tar.gz', fingerprint: true   // зберегти файли при збірці

// Shared Library: спільний код для сотень Jenkinsfile (окремий репозиторій, vars/standardPipeline.groovy)

Спільна бібліотека прибирає копіювання однакових Jenkinsfile між репозиторіями: виправили крок у бібліотеці — виправилось у всіх проєктах.

Масштабування і зручності#

  • Multibranch / Organization Folder — сканує організацію GitHub/Bitbucket, знаходить Jenkinsfile і автоматично створює задачі для кожного репозиторію, гілки й PR. Запуск — через webhook або періодично.
  • Docker-агенти — збірка в контейнері: не треба встановлювати інструменти на сервер, можна кілька версій одного інструмента; також підтримується Kubernetes.
  • Shared Libraries (DRY) — спільний код для всіх задач, завантажується з Git-репозиторію.
  • Інструменти: Blue Ocean (візуалізація і редактор конвеєрів, інтеграція з PR), Snippet Generator (http://jenkins:8080/pipeline-syntax), Directive Generator, Replay (перезапустити змінений конвеєр без коміту), автоконвертація Freestyle-задач, лінтер Jenkinsfile з командного рядка, автодоповнення в IntelliJ (GDSL), unit-тести конвеєрів.

З чату лекції: комітити в головну гілку вирішує команда (зазвичай через PR), а не DevOps одноосібно; Jenkins і альтернативи (GitHub Actions — наступна лекція) краще вивчати окремо — встановлення і налаштування, потім інтеграції.

Тригери збірки, плагіни і правила CI#

ТригерЯк працює
Build Nowручний запуск кнопкою
Poll SCMJenkins сам періодично питає репозиторій «чи є нові коміти» (розклад у форматі cron, напр. H/5 * * * *)
Webhook (GitHub hook trigger)репозиторій сам повідомляє Jenkins про push — швидше і без зайвих опитувань
Build periodicallyза розкладом незалежно від змін (нічні збірки)
Build after other projectsпісля успішної збірки іншої задачі (upstream/downstream)

H у розкладі Jenkins — «хеш»: Jenkins сам обирає хвилину, щоб сотні задач не стартували в одну мить.

Плагіни — основний спосіб розширити Jenkins (Git, Pipeline, Docker, Credentials, Blue Ocean тощо), встановлюються через Manage Jenkins → Plugins. Результати тестів публікують кроком junit, готові файли зберігають кроком archiveArtifacts.

Правила CI

  • Комітьте в спільну гілку часто, малими порціями.
  • Кожен коміт автоматично збирається і тестується.
  • Зламану збірку лагодять першочергово — «червоний» main блокує всіх.
  • Збірка має бути швидкою (хвилини, а не години).
  • Тестове середовище має бути схожим на production.

Типові помилки#

Збірки зручно запускати прямо на контролері Jenkins.
Код збірки на контролері має доступ до JENKINS_HOME і всіх секретів. Збірки — на агентах, executors контролера = 0.
Секрет у sh "docker login -p ${PASS}" безпечний, бо Jenkins маскує його.
Подвійні лапки — інтерполяція Groovy: секрет потрапляє в текст команди. Пишіть sh '... "$PASS" ...' і передавайте через stdin.
UNSTABLE — те саме, що FAILURE.
UNSTABLE: збірка відбулась, але частина тестів впала. FAILURE: крок завершився помилкою.
Налаштовувати конвеєр кліками в UI (Freestyle) і ніде його не зберігати.
Jenkinsfile у репозиторії: рев'ю, історія змін, відтворюваність. Для міграції є автоконвертація Freestyle → Pipeline.
Писати пароль прямо в Jenkinsfile.
Секрети зберігають у Jenkins Credentials і підставляють через credentials('id') в environment.
Плутати stage і step.
Stage — етап конвеєра (Build, Test, Deploy), steps — список дій усередині етапу (sh, echo, git).
Тримати input всередині агента, що займає executor на дні.
Для очікування схвалення використовують agent none на верхньому рівні, щоб не блокувати ресурси.
