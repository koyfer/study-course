GitHub Actions: workflow, jobs, runners, secrets і автоматичний деплой

GitHub Actions — CI/CD, вбудований просто в GitHub: конвеєр описується YAML-файлом у репозиторії і запускається на події на кшталт push чи pull request. Розбираємо компоненти і реальний workflow «тести → збірка → деплой».

≈ 16 хв читання 10 питань самоперевірки Не опрацьовано

Чого ви навчитесь#

  • Назвати 6 компонентів GitHub Actions і пояснити, як вони пов'язані.
  • Створити workflow-файл у правильному каталозі і прочитати його синтаксис: on, jobs, runs-on, steps, uses, with, run.
  • Використати matrix для тестування на кількох версіях і secrets для токенів.
  • Розібрати workflow «тести → збірка → деплой на Heroku» рядок за рядком.
  • Порівняти GitHub Actions і Jenkins.

Що таке GitHub Actions#

GitHub Actions автоматизує робочі процеси розробки — збирання, тести, деплой, рев'ю, керування гілками й задачами — просто в GitHub. Actions — це повторно використовувані скрипти: можна писати свої (JavaScript, Docker тощо) або брати готові з GitHub Marketplace: надіслати повідомлення в Slack (slack-send), завантажити звіт покриття (codecov), задеплоїти в Google Cloud (setup-gcloud). Готові дії «зшиваються» у workflow.

Компоненти#

WorkflowРобочий процес

Налаштований автоматизований процес, що запускає один або кілька jobs. YAML-файл у репозиторії.

EventПодія

Активність у репозиторії, що запускає workflow: push, pull request, розклад, ручний запуск.

JobЗавдання

Набір кроків, що виконуються на одному runner послідовно.

StepКрок

Або uses (готова дія), або run (shell-команда) — не обидва в одному кроці.

ActionДія

Застосунок для платформи, що виконує складну повторювану задачу (checkout коду, встановлення Node).

RunnerВиконавець

Сервер, що виконує jobs: GitHub-hosted (ubuntu-latest, windows-latest, macos-latest) або self-hosted — на вашому ПК чи в хмарі.

Як увімкнути#

  1. Відкрити репозиторій проєкту на GitHub.
  2. Створити каталог .github/workflows/ (саме workflows, у множині) — або вкладка Actions → Set up a workflow чи готовий шаблон.
  3. Додати файл у форматі YAML, напр. my-pipeline-ver-1.yml.
  4. Щойно файл потрапив у репозиторій, GitHub Actions автоматично починає реагувати на описані події. Результати — на вкладці Actions.

Синтаксис: ключі workflow#

КлючЗначення
nameНазва для відображення в інтерфейсі (необов'язкова)
onПодії-тригери, напр. push у гілку master
jobsПерелік jobs; ключ (build) — ідентифікатор
runs-onТип runner
strategy.matrixЗапустити job кілька разів з різними параметрами
stepsСписок кроків job
usesГотова дія: власник/репо@версія, локальна папка або Docker-образ
withПараметри для дії (наприклад, версія Node)
runShell-команда; | дозволяє кілька рядків
envЗмінні оточення кроку/job

actions/checkout завантажує код репозиторію і гілки, на якій запущено workflow — без нього в runner немає вашого коду. actions/setup-node встановлює Node.js потрібної версії. Вихідний код будь-якої дії можна переглянути на GitHub за назвою (версія — після @).

Розбір: тести, збірка і деплой на Heroku#

Workflow зі сторінки курсу (Node.js-застосунок):

name: CI
on:
  push:
    branches:
      - master                               # 1. запуск на push у master
jobs:
  build:
    runs-on: ubuntu-latest                   # 2. GitHub-hosted runner
    strategy:
      matrix:
        node-version: [14.x, 16.x]           # 3. job запуститься двічі
    steps:
    - uses: actions/checkout@v1              # 4. забрати код
    - name: Use Node.js ${{ matrix.node-version }}
      uses: actions/setup-node@v1            # 5. встановити Node
      with:
        node-version: ${{ matrix.node-version }}
    - name: yarn install
      run: yarn install                      # 6. залежності
    - name: yarn test
      run: yarn test
      env:
        CI: true                             # 7. тести в CI-режимі
    - name: yarn build
      run: yarn run build --if-present       # 8. збірка, якщо є скрипт build
    - name: Add remote origin
      run: git remote add heroku https://heroku:${{ secrets.HEROKU_API_KEY }}@git.heroku.com/${{ secrets.HEROKU_APP_NAME }}.git
    - name: Deploy to Heroku
      run: git push heroku HEAD:master -f    # 9. деплой = push у git-репозиторій Heroku
Актуальність прикладу

Приклад 2022 року. Відтоді Heroku прибрав безкоштовний тариф (листопад 2022), Node 14/16 більше не підтримуються, а дії мають новіші версії (actions/checkout@v4, actions/setup-node@v4). Логіку workflow це не змінює.

Secrets, обмеження, self-hosted runners#

Опублікований токен — великий ризик. Тому в GitHub є secrets: Settings → Secrets and variables → Actions, створюєте, напр., MY_TOKEN, і в workflow пишете ${{ secrets.MY_TOKEN }}. Значення шифрується і маскується в логах. Також щоразу автоматично доступний ${{ secrets.GITHUB_TOKEN }} для роботи з цим репозиторієм.

  • Self-hosted runner — власна машина (ПК, сервер, хмарна ВМ) реєструється в репозиторії (Settings → Actions → Runners) і виконує jobs: доступ до внутрішньої мережі, своє залізо, без хвилин GitHub.
  • Обмеження: у PDF наведено ліміти на кшталт «до 58 хвилин на workflow» — вони не відповідають поточній документації (зараз, наприклад, job на GitHub-hosted runner може тривати до 6 годин). Ліміти і ціни змінюються — перевіряйте розділ «Usage limits» документації GitHub. Публічні репозиторії мають безкоштовні хвилини.
  • Marketplace: Danger — автоматичне код-рев'ю, Dependabot — оновлення вразливих залежностей, Codecov — звіти покриття.
  • Бейдж статусу в README: ![](https://github.com/<user>/<repo>/actions/workflows/<file>.yml/badge.svg) (у PDF — старіший формат через /workflows/<name>/badge.svg).

Довідково: деплой статичного сайту на GitHub Pages#

Цей самий навчальний сайт публікується на GitHub Pages. Сучасний мінімальний workflow для статичного сайту (без збирання) виглядає так:

name: Deploy site
on:
  push:
    branches: [main]
permissions:
  contents: read
  pages: write
  id-token: write
jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: github-pages
    steps:
      - uses: actions/checkout@v4
      - uses: actions/upload-pages-artifact@v3
        with:
          path: .                       # що публікувати
      - uses: actions/deploy-pages@v4    # викласти на Pages

Тригери, залежності jobs, умови, кеш і артефакти#

on:
  push: { branches: [main] }
  pull_request:
  schedule: [{ cron: "0 3 * * 1" }]   # щопонеділка о 03:00 UTC
  workflow_dispatch:                  # кнопка «Run workflow» у вкладці Actions
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20, cache: npm }   # кеш залежностей між запусками
      - run: npm ci && npm test && npm run build
      - uses: actions/upload-artifact@v4         # передати збірку наступному job
        with: { name: dist, path: dist }
  deploy:
    needs: build                                 # чекати успішного build
    if: github.ref == 'refs/heads/main'          # лише для main
    runs-on: ubuntu-latest
    steps:
      - uses: actions/download-artifact@v4
        with: { name: dist }
  • Jobs за замовчуванням ідуть паралельно; needs робить їх послідовними.
  • Кожен job стартує на чистому runner, тож файли між jobs передають через артефакти (upload-artifact / download-artifact), а залежності пришвидшують кешем (actions/cache або cache: у setup-діях).
  • if: вмикає крок чи job за умовою (гілка, подія, результат попереднього кроку).
  • Розклад schedule використовує формат cron (як у Linux) і час UTC.

Типові помилки#

Файл у .github/workflow/ — і нічого не запускається.
Правильний каталог — .github/workflows/ (у множині), формат — YAML (.yml/.yaml).
Забути actions/checkout і дивуватися, що yarn install не знаходить package.json.
Runner стартує порожнім — код треба завантажити першим кроком.
uses і run в одному кроці.
Кожен крок — або дія (uses), або команда (run). Розділіть на два кроки.
Вставити API-ключ прямо в YAML.
Репозиторій (і його історія) може бути публічним. Ключ — у Secrets, у файлі — лише ${{ secrets.NAME }}.
Помилки відступів у YAML.
YAML чутливий до відступів: лише пробіли, однакова вкладеність для елементів одного рівня.
