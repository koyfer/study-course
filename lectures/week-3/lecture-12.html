GitHub Actions: workflow, jobs, runners, secrets і автоматичний деплой

GitHub Actions — CI/CD, вбудований просто в GitHub: конвеєр описується YAML-файлом у репозиторії і запускається на події на кшталт push чи pull request. Розбираємо компоненти і реальний workflow «тести → збірка → деплой».

≈ 60 хв читання 25 питань самоперевірки Не опрацьовано

Чого ви навчитесь#

  • Назвати 6 компонентів GitHub Actions і пояснити, як вони пов'язані.
  • Створити workflow-файл у правильному каталозі і прочитати його синтаксис: on, jobs, runs-on, steps, uses, with, run.
  • Використати matrix для тестування на кількох версіях і secrets для токенів.
  • Розібрати workflow «тести → збірка → деплой на Heroku» рядок за рядком.
  • Порівняти GitHub Actions і Jenkins.
  • Використовувати контексти й вирази ${{ }}, outputs кроків і jobs, GITHUB_OUTPUT, GITHUB_ENV, функції статусу failure()/always().
  • Налаштувати середовища зі схваленням, мінімальні permissions, OIDC до хмари, concurrency, services-контейнери.
  • Написати повний workflow: матриця тестів, збірка і публікація образу в GHCR, деплой у staging і production.
  • Налаштовувати фільтри подій, ручний запуск з inputs, права GITHUB_TOKEN, concurrency і матриці.
  • Використовувати сервісні контейнери, кеш і артефакти, reusable workflow, OIDC-деплой, налагоджувати і захищати workflow.

Що таке GitHub Actions#

GitHub Actions автоматизує робочі процеси розробки — збирання, тести, деплой, рев'ю, керування гілками й задачами — просто в GitHub. Actions — це повторно використовувані скрипти: можна писати свої (JavaScript, Docker тощо) або брати готові з GitHub Marketplace: надіслати повідомлення в Slack (slack-send), завантажити звіт покриття (codecov), задеплоїти в Google Cloud (setup-gcloud). Готові дії «зшиваються» у workflow.

Компоненти#

WorkflowРобочий процес

Налаштований автоматизований процес, що запускає один або кілька jobs. YAML-файл у репозиторії.

EventПодія

Активність у репозиторії, що запускає workflow: push, pull request, розклад, ручний запуск.

JobЗавдання

Набір кроків, що виконуються на одному runner послідовно.

StepКрок

Або uses (готова дія), або run (shell-команда) — не обидва в одному кроці.

ActionДія

Застосунок для платформи, що виконує складну повторювану задачу (checkout коду, встановлення Node).

RunnerВиконавець

Сервер, що виконує jobs: GitHub-hosted (ubuntu-latest, windows-latest, macos-latest) або self-hosted — на вашому ПК чи в хмарі.

Як увімкнути#

  1. Відкрити репозиторій проєкту на GitHub.
  2. Створити каталог .github/workflows/ (саме workflows, у множині) — або вкладка Actions → Set up a workflow чи готовий шаблон.
  3. Додати файл у форматі YAML, напр. my-pipeline-ver-1.yml.
  4. Щойно файл потрапив у репозиторій, GitHub Actions автоматично починає реагувати на описані події. Результати — на вкладці Actions.

Події і керування запуском детально#

Фільтри подій: коли саме запускати

on:
  push:
    branches: [main, 'release/**']       # лише ці гілки
    tags: ['v*']                          # і теги версій
    paths-ignore: ['docs/**', '**.md']    # зміни лише в документації не запускають CI
  pull_request:
    types: [opened, synchronize, reopened]   # типи активності (за замовчуванням саме ці)
    branches: [main]                      # PR, що націлені В main
  schedule:
    - cron: '17 3 * * 1-5'                # будні о 03:17 UTC (не за київським часом!)
  workflow_dispatch:                      # кнопка «Run workflow» у вкладці Actions
    inputs:
      environment:
        type: choice
        options: [staging, production]
        default: staging
      dry_run:
        type: boolean
        default: true
  release:
    types: [published]                    # коли опубліковано реліз на GitHub
  workflow_run:
    workflows: ["CI"]                     # після завершення іншого workflow
    types: [completed]
ПодіяТипове використанняНюанси
pushCI на кожен коміт, деплой з main, реліз з тегуbranches і tags фільтрують незалежно; paths — за зміненими файлами
pull_requestперевірка PR перед злиттямз форків секрети недоступні, а GITHUB_TOKEN має лише читання — захист від крадіжки секретів
scheduleнічні збірки, очищення, звітичас — UTC; мінімальний інтервал 5 хв; запуск може запізнюватися у години пік; працює з default-гілки
workflow_dispatchручний деплой з параметрамизначення в inputs.environment; також запускається через API або gh workflow run
releaseзбірка і публікація пакетів при релізітип published — найчастіший
workflow_runдеплой після успішного CI іншого workflowперевіряйте github.event.workflow_run.conclusion == 'success'
repository_dispatchзапуск із зовнішньої системи через APIдовільний event_type і payload

Права GITHUB_TOKEN

Для кожного запуску GitHub автоматично створює токен GITHUB_TOKEN, дійсний лише під час job. Його права краще звужувати явно — принцип найменших привілеїв:

permissions:
  contents: read          # читати код
  packages: write         # публікувати образ у GHCR
  pull-requests: write    # коментувати PR (наприклад, план Terraform)
  id-token: write         # отримувати OIDC-токен для входу в AWS/GCP/Azure без ключів

Якщо задати permissions, усі не перелічені права стають none.

Контроль виконання: concurrency, timeout, помилки

concurrency:
  group: deploy-${{ github.ref }}       # один деплой на гілку одночасно
  cancel-in-progress: true              # новий запуск скасовує попередній незавершений

jobs:
  test:
    runs-on: ubuntu-latest
    timeout-minutes: 20                 # за замовчуванням 360 хв (6 год) — краще обмежити
    strategy:
      fail-fast: false                  # не скасовувати інші комбінації матриці, якщо одна впала
      max-parallel: 3
      matrix:
        os: [ubuntu-latest, windows-latest]
        node: [18, 20, 22]
        exclude:
          - os: windows-latest
            node: 18                    # прибрати одну комбінацію
        include:
          - os: ubuntu-latest
            node: 22
            coverage: true              # додати змінну лише для цієї комбінації
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: '${{ matrix.node }}' }
      - run: npm ci && npm test
      - run: npm run coverage
        if: ${{ matrix.coverage }}
      - run: npm run lint
        continue-on-error: true         # падіння lint не валить job (лише попередження)

Скільки job створить ця матриця: 2 ОС × 3 версії = 6, мінус 1 виключена = 5. include тут не додає нову комбінацію, а лише змінну до вже існуючої (ubuntu + 22).

Умови if: типові вирази

ВиразЗначення
if: github.ref == 'refs/heads/main'лише для гілки main
if: startsWith(github.ref, 'refs/tags/v')лише для тегів версій
if: github.event_name == 'pull_request'лише в PR
if: failure()крок виконається, лише якщо попередній впав (сповіщення)
if: always()завжди, навіть після помилки чи скасування (зібрати звіти)
if: success() && inputs.dry_run == falseкомбінація з вхідним параметром
if: contains(github.event.head_commit.message, '[skip deploy]') == falseпропустити, якщо в повідомленні коміту є мітка

За замовчуванням кожен крок має неявну умову success(): після першого впалого кроку наступні пропускаються.

Вирази, контексти, outputs і змінні оточення#

Вирази в workflow пишуть у ${{ … }}. Усередині доступні контексти — об'єкти з інформацією про запуск.

КонтекстЩо міститьПриклад
githubподія, репозиторій, гілка, коміт, авторgithub.ref, github.sha, github.event_name, github.actor
envзмінні оточення з env:env.IMAGE
vars / secretsнесекретні змінні / секрети з налаштувань репозиторіюvars.REGION, secrets.DOCKER_TOKEN
matrixпоточна комбінація матриціmatrix.node
stepsрезультати і outputs попередніх кроків з idsteps.meta.outputs.tag
needsрезультати і outputs jobs-залежностейneeds.build.outputs.version
runnerінформація про runnerrunner.os
inputsпараметри ручного запуску або reusable workflowinputs.environment

Передача значень між кроками і jobs

jobs:
  build:
    runs-on: ubuntu-latest
    outputs:
      version: ${{ steps.meta.outputs.version }}        # зробити output кроку output-ом job
    steps:
      - id: meta
        run: echo "version=1.4.${{ github.run_number }}" >> "$GITHUB_OUTPUT"
      - run: echo "DEPLOY_ENV=staging" >> "$GITHUB_ENV"   # змінна для всіх наступних кроків job
      - run: echo "Версія ${{ steps.meta.outputs.version }}, середовище $DEPLOY_ENV"
      - run: echo "### Зібрано ${{ steps.meta.outputs.version }}" >> "$GITHUB_STEP_SUMMARY"   # звіт на сторінці запуску
  deploy:
    needs: build
    runs-on: ubuntu-latest
    steps:
      - run: echo "Деплою ${{ needs.build.outputs.version }}"

Стандартні змінні оточення runner: GITHUB_SHA, GITHUB_REF, GITHUB_REPOSITORY, GITHUB_RUN_NUMBER, GITHUB_WORKSPACE, RUNNER_OS. Різниця записів: ${{ env.X }} підставляє GitHub до запуску кроку, а $X розкриває shell під час виконання.

Умови і функції статусу

- name: Notify on failure
  if: failure()                                        # лише якщо попередній крок впав
  run: ./notify.sh "Build failed: ${{ github.sha }}"
- name: Cleanup
  if: always()                                         # завжди, навіть після помилки чи скасування
  run: docker compose down
- name: Only on tags
  if: startsWith(github.ref, 'refs/tags/v')
  run: echo "Release ${{ github.ref_name }}"

За замовчуванням кожен крок має неявну умову success(): після першої помилки решта кроків пропускається. Функції: success(), failure(), always(), cancelled(); рядкові contains(), startsWith(), endsWith(), format(), toJSON().

Середовища, схвалення і безпека#

Environments: Continuous Delivery в GitHub Actions

У Settings → Environments створюють середовища (staging, production) з правилами захисту: required reviewers (хтось має натиснути «Approve»), таймер очікування, дозволені гілки, окремі секрети середовища. Job з environment: production зупиняється і чекає схвалення — це аналог кроку input у Jenkins.

deploy-prod:
  needs: deploy-staging
  runs-on: ubuntu-latest
  environment:
    name: production
    url: https://shop.example.com
  steps:
    - run: ./deploy.sh production

Безпека workflow

  • Мінімальні права GITHUB_TOKEN через permissions: на рівні workflow або job.
  • OIDC замість довгоживучих ключів: workflow отримує короткоживучий токен від хмари (AWS, Azure, GCP) через permissions: id-token: write і дію на кшталт aws-actions/configure-aws-credentials. Ключі доступу не зберігаються в secrets взагалі.
  • Фіксуйте сторонні дії на повний SHA коміту (uses: org/action@a1b2c3…) або хоча б мажорну версію від перевіреного автора: тег може бути перезаписаний.
  • Секрети не передаються у workflow, запущені з pull request з форків. Тригер pull_request_target їх отримує — тому в ньому ніколи не виконують код із PR.
  • Dependabot оновлює і залежності застосунку, і версії дій у workflow (.github/dependabot.yml).

Повторне використання

  • Reusable workflow: файл з on: workflow_call, який викликають з інших workflow як job: uses: org/ci/.github/workflows/build.yml@main.
  • Composite action: набір кроків, оформлений як власна дія з action.yml.
  • Starter workflows і Marketplace — готові шаблони і дії.

Розбір: тести, збірка і деплой на Heroku#

Workflow зі сторінки курсу (Node.js-застосунок):

name: CI
on:
  push:
    branches:
      - master                               # 1. запуск на push у master
jobs:
  build:
    runs-on: ubuntu-latest                   # 2. GitHub-hosted runner
    strategy:
      matrix:
        node-version: [14.x, 16.x]           # 3. job запуститься двічі
    steps:
    - uses: actions/checkout@v1              # 4. забрати код
    - name: Use Node.js ${{ matrix.node-version }}
      uses: actions/setup-node@v1            # 5. встановити Node
      with:
        node-version: ${{ matrix.node-version }}
    - name: yarn install
      run: yarn install                      # 6. залежності
    - name: yarn test
      run: yarn test
      env:
        CI: true                             # 7. тести в CI-режимі
    - name: yarn build
      run: yarn run build --if-present       # 8. збірка, якщо є скрипт build
    - name: Add remote origin
      run: git remote add heroku https://heroku:${{ secrets.HEROKU_API_KEY }}@git.heroku.com/${{ secrets.HEROKU_APP_NAME }}.git
    - name: Deploy to Heroku
      run: git push heroku HEAD:master -f    # 9. деплой = push у git-репозиторій Heroku
Актуальність прикладу

Приклад 2022 року. Відтоді Heroku прибрав безкоштовний тариф (листопад 2022), Node 14/16 більше не підтримуються, а дії мають новіші версії (actions/checkout@v4, actions/setup-node@v4). Логіку workflow це не змінює.

Runners, сервісні контейнери, повторне використання і деплой без ключів#

Де виконується job

Runnerruns-onОсобливості
GitHub-hosted Linuxubuntu-latest, ubuntu-24.04свіжа ВМ на кожен job: Docker, Python, Node, Java, AWS CLI вже встановлені; після job ВМ знищується
GitHub-hosted Windows / macOSwindows-latest, macos-latestдля збірок під ці платформи; хвилини для приватних репозиторіїв рахуються з коефіцієнтом
Self-hosted[self-hosted, linux, x64, gpu]ваш сервер з агентом runner: доступ до внутрішньої мережі, особливе залізо, без лімітів хвилин; але оновлення і безпека — на вас
Self-hosted runner і публічні репозиторії

Не підключайте self-hosted runner до публічного репозиторію: будь-хто може відкрити PR зі шкідливим кодом, який виконається на вашому сервері всередині вашої мережі.

Сервісні контейнери: справжня БД для інтеграційних тестів

jobs:
  integration:
    runs-on: ubuntu-latest
    services:
      postgres:
        image: postgres:16
        env:
          POSTGRES_PASSWORD: test
        ports: ['5432:5432']
        options: >-
          --health-cmd "pg_isready -U postgres"
          --health-interval 5s --health-retries 10
    steps:
      - uses: actions/checkout@v4
      - run: pip install -r requirements.txt
      - run: pytest tests/integration
        env:
          DATABASE_URL: postgres://postgres:test@localhost:5432/postgres

Коли кроки виконуються прямо на runner, сервіс доступний на localhost через опубліковані порти. Якщо job сам працює в контейнері (container:), до сервісу звертаються за іменем postgres.

Кеш і артефакти: не плутати

CacheArtifacts
Призначенняпришвидшити повторні запуски (залежності)передати результат між jobs або зберегти для людей
Що зберігають~/.npm, ~/.cache/pip, ~/.m2зібраний dist/, звіти тестів, логи
Ключхеш lock-файла: ${{ hashFiles('**/package-lock.json') }}ім'я артефакту
Діїactions/cache або вбудований cache: npm у setup-nodeactions/upload-artifact / actions/download-artifact
Гарантія наявностіні: кеш можуть витіснити, workflow має працювати і без ньоготак, протягом строку зберігання (за замовчуванням 90 днів)
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20, cache: npm }       # кеш ~/.npm за package-lock.json
      - run: npm ci && npm run build
      - uses: actions/upload-artifact@v4
        with: { name: site, path: dist/ }
  deploy:
    needs: build                                     # інший job = інша ВМ: файлів build тут немає
    runs-on: ubuntu-latest
    steps:
      - uses: actions/download-artifact@v4
        with: { name: site, path: dist/ }
      - run: ls dist/

Повторне використання: reusable workflow і composite action

Reusable workflow

  • цілий workflow з jobs, що викликається з інших: on: workflow_call
  • виклик: jobs: ci: uses: acme/.github/.github/workflows/node-ci.yml@v1
  • приймає inputs і secrets
  • для стандартизації CI в багатьох репозиторіях

Composite action

  • набір кроків, оформлений як дія з action.yml
  • виклик як звичайного кроку: - uses: ./.github/actions/setup-app
  • виконується в тому самому job і на тому самому runner
  • для повторюваних послідовностей кроків
# .github/actions/setup-app/action.yml — composite action
name: Setup app
inputs:
  node-version: { default: '20' }
runs:
  using: composite
  steps:
    - uses: actions/setup-node@v4
      with: { node-version: '${{ inputs.node-version }}', cache: npm }
    - run: npm ci
      shell: bash                        # у composite-кроках run shell обов'язковий

Деплой в AWS без довгострокових ключів (OIDC)

Замість того, щоб класти AWS_ACCESS_KEY_ID і AWS_SECRET_ACCESS_KEY у секрети, GitHub видає короткоживучий OIDC-токен, а AWS обмінює його на тимчасові облікові дані ролі, якій ви довіряєте лише для цього репозиторію.

permissions:
  id-token: write        # дозволити отримати OIDC-токен
  contents: read
jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: production
    steps:
      - uses: actions/checkout@v4
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789012:role/github-deploy
          aws-region: eu-central-1
      - run: aws s3 sync dist/ s3://shop-static --delete

У довірчій політиці ролі обмежують, з якого репозиторію і гілки її можна взяти (умова на token.actions.githubusercontent.com:sub, наприклад repo:acme/shop:ref:refs/heads/main). Немає статичних ключів — нічого витікати.

Secrets, обмеження, self-hosted runners#

Опублікований токен — великий ризик. Тому в GitHub є secrets: Settings → Secrets and variables → Actions, створюєте, напр., MY_TOKEN, і в workflow пишете ${{ secrets.MY_TOKEN }}. Значення шифрується і маскується в логах. Також щоразу автоматично доступний ${{ secrets.GITHUB_TOKEN }} для роботи з цим репозиторієм.

  • Self-hosted runner — власна машина (ПК, сервер, хмарна ВМ) реєструється в репозиторії (Settings → Actions → Runners) і виконує jobs: доступ до внутрішньої мережі, своє залізо, без хвилин GitHub.
  • Обмеження: у PDF наведено ліміти на кшталт «до 58 хвилин на workflow» — вони не відповідають поточній документації (зараз, наприклад, job на GitHub-hosted runner може тривати до 6 годин). Ліміти і ціни змінюються — перевіряйте розділ «Usage limits» документації GitHub. Публічні репозиторії мають безкоштовні хвилини.
  • Marketplace: Danger — автоматичне код-рев'ю, Dependabot — оновлення вразливих залежностей, Codecov — звіти покриття.
  • Бейдж статусу в README: ![](https://github.com/<user>/<repo>/actions/workflows/<file>.yml/badge.svg) (у PDF — старіший формат через /workflows/<name>/badge.svg).

Довідково: деплой статичного сайту на GitHub Pages#

Цей самий навчальний сайт публікується на GitHub Pages. Сучасний мінімальний workflow для статичного сайту (без збирання) виглядає так:

name: Deploy site
on:
  push:
    branches: [main]
permissions:
  contents: read
  pages: write
  id-token: write
jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: github-pages
    steps:
      - uses: actions/checkout@v4
      - uses: actions/upload-pages-artifact@v3
        with:
          path: .                       # що публікувати
      - uses: actions/deploy-pages@v4    # викласти на Pages

Тригери, залежності jobs, умови, кеш і артефакти#

on:
  push: { branches: [main] }
  pull_request:
  schedule: [{ cron: "0 3 * * 1" }]   # щопонеділка о 03:00 UTC
  workflow_dispatch:                  # кнопка «Run workflow» у вкладці Actions
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20, cache: npm }   # кеш залежностей між запусками
      - run: npm ci && npm test && npm run build
      - uses: actions/upload-artifact@v4         # передати збірку наступному job
        with: { name: dist, path: dist }
  deploy:
    needs: build                                 # чекати успішного build
    if: github.ref == 'refs/heads/main'          # лише для main
    runs-on: ubuntu-latest
    steps:
      - uses: actions/download-artifact@v4
        with: { name: dist }
  • Jobs за замовчуванням ідуть паралельно; needs робить їх послідовними.
  • Кожен job стартує на чистому runner, тож файли між jobs передають через артефакти (upload-artifact / download-artifact), а залежності пришвидшують кешем (actions/cache або cache: у setup-діях).
  • if: вмикає крок чи job за умовою (гілка, подія, результат попереднього кроку).
  • Розклад schedule використовує формат cron (як у Linux) і час UTC.

Повний workflow: тести з матрицею → Docker-образ у GHCR → деплой зі схваленням#

name: CI/CD
on:
  push:
    branches: [main]
  pull_request:

permissions:
  contents: read
  packages: write                       # публікація образу в GitHub Container Registry

env:
  IMAGE: ghcr.io/${{ github.repository }}

jobs:
  test:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        python: ["3.11", "3.12"]        # дві паралельні копії job
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: ${{ matrix.python }}
          cache: pip
      - run: pip install -r requirements.txt
      - run: pytest --junitxml=report.xml
      - uses: actions/upload-artifact@v4
        if: always()
        with:
          name: report-${{ matrix.python }}
          path: report.xml

  image:
    needs: test
    if: github.event_name == 'push'      # для PR лише тести
    runs-on: ubuntu-latest
    outputs:
      tag: ${{ steps.vars.outputs.tag }}
    steps:
      - uses: actions/checkout@v4
      - id: vars
        run: echo "tag=${GITHUB_SHA::7}" >> "$GITHUB_OUTPUT"
      - uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      - uses: docker/build-push-action@v6
        with:
          push: true
          tags: ${{ env.IMAGE }}:${{ steps.vars.outputs.tag }}

  deploy-staging:
    needs: image
    runs-on: ubuntu-latest
    environment: staging
    steps:
      - run: echo "deploy ${{ env.IMAGE }}:${{ needs.image.outputs.tag }} to staging"

  deploy-production:
    needs: [image, deploy-staging]
    runs-on: ubuntu-latest
    environment: production              # зупиниться до схвалення рецензентом
    concurrency: production
    steps:
      - run: echo "deploy ${{ env.IMAGE }}:${{ needs.image.outputs.tag }} to production"

Що тут відбувається

  1. На кожен push у main і кожен pull request запускається test у двох версіях Python паралельно; звіти зберігаються як артефакти навіть при падінні тестів (if: always()).
  2. Лише для push (не для PR) job image збирає Docker-образ з тегом за коротким хешем коміту і публікує в GHCR, використовуючи вбудований GITHUB_TOKEN з правом packages: write.
  3. deploy-staging розгортає автоматично (Continuous Deployment у staging).
  4. deploy-production чекає схвалення в середовищі production (Continuous Delivery); concurrency не дає запустити два деплої одночасно.

Порівняйте з конвеєром Jenkins з лекції 11: етапи ті самі, різниця — у синтаксисі (YAML замість Groovy), у тому, хто підтримує сервер (GitHub замість вас), і в механізмі схвалення (environment замість input).

Налагодження, безпека і обмеження GitHub Actions#

Як знайти причину падіння

  1. Вкладка Actions → запуск → job → розгорнути червоний крок. Читайте з кінця: перша помилка зазвичай за кілька рядків до Process completed with exit code 1.
  2. Re-run jobs → Enable debug logging — повторний запуск з детальними логами runner і кроків (те саме дає секрет або змінна ACTIONS_STEP_DEBUG=true).
  3. Вивести контекст: - run: echo '${{ toJSON(github.event) }}' — побачити, що саме прийшло в подію (не робіть цього для контекстів із секретами).
  4. Локально: утиліта act запускає workflow у Docker на вашій машині (з обмеженнями).
  5. Перевірити синтаксис: actionlint знаходить помилки в YAML і виразах ще до push.

Push є, а workflow не запустивсяфільтри branches/paths не збіглися, або workflow є лише в іншій гілціперевірити on:; для schedule і workflow_dispatch файл має бути в default-гілці

Безпека workflow: чек-лист

  • Найменші права: permissions: contents: read на рівні workflow, ширші — лише для job, якому треба.
  • Фіксуйте версії дій: uses: actions/checkout@v4 — мінімум; для сторонніх дій надійніше повний SHA коміту (@8f4b7f8…), бо тег можна перевісити на шкідливий код.
  • Обережно з pull_request_target: він виконується в контексті базового репозиторію з доступом до секретів; якщо в ньому робити checkout і запускати код з PR форку — це прямий шлях до крадіжки секретів.
  • Не підставляйте недовірені дані прямо в run: run: echo "${{ github.event.pull_request.title }}" дозволяє ін'єкцію команд через заголовок PR. Безпечно — через змінну оточення: env: TITLE: ${{ github.event.pull_request.title }} і echo "$TITLE".
  • Environments з обов'язковим схваленням для production і секрети, прив'язані до environment, а не до всього репозиторію.
  • OIDC замість довгострокових хмарних ключів.
  • Dependabot для оновлення версій дій і залежностей.

Типові помилки#

Файли, створені в одному job, доступні в наступному.
Кожен job стартує на чистому runner. Передавайте файли артефактами, значення — через outputs.
Сторонню дію безпечно підключати за тегом @main.
Гілку і тег можуть змінити. Фіксуйте дію на SHA коміту або перевірену мажорну версію.
Для доступу до AWS треба зберегти ключі в secrets.
Краще OIDC: короткоживучі облікові дані видаються на кожен запуск, довгоживучих ключів немає.
Файл у .github/workflow/ — і нічого не запускається.
Правильний каталог — .github/workflows/ (у множині), формат — YAML (.yml/.yaml).
Забути actions/checkout і дивуватися, що yarn install не знаходить package.json.
Runner стартує порожнім — код треба завантажити першим кроком.
uses і run в одному кроці.
Кожен крок — або дія (uses), або команда (run). Розділіть на два кроки.
Вставити API-ключ прямо в YAML.
Репозиторій (і його історія) може бути публічним. Ключ — у Secrets, у файлі — лише ${{ secrets.NAME }}.
Помилки відступів у YAML.
YAML чутливий до відступів: лише пробіли, однакова вкладеність для елементів одного рівня.
