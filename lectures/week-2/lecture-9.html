Віртуалізація і контейнери: гіпервізор, namespaces, Docker і Dockerfile

«Один застосунок — один сервер» — дорого. Віртуалізація ділить залізо між ОС, а контейнери йдуть далі: ділять одне ядро між ізольованими застосунками. Docker зробив контейнери масовими.

Чого ви навчитесь#

  • Порівняти віртуальні машини і контейнери за архітектурою та витратою ресурсів.
  • Назвати механізми ядра Linux, на яких тримаються контейнери: namespaces, cgroups, capabilities.
  • Розрізняти образ, контейнер, registry і пояснити архітектуру Docker Engine.
  • Написати Dockerfile і пояснити різницю між RUN, CMD, ENTRYPOINT, EXPOSE.
  • Користуватися основними командами: pull, build, run -p, ps, exec, stop, rm, rmi.
  • Розрізняти гіпервізори типу 1 і 2, пояснити шари образу і томи, підняти стек через Docker Compose і назвати базові об'єкти Kubernetes.
  • Розрізняти shell і exec форми, CMD і ENTRYPOINT, ARG і ENV, COPY і ADD; писати багатоетапний Dockerfile за найкращими практиками.
  • Запускати контейнери з потрібними опціями, мережами, томами, обмеженнями; публікувати образи в реєстр; діагностувати за кодами виходу.
  • Пояснити архітектуру Kubernetes і об'єкти Pod, Deployment, Service, Ingress, ConfigMap, Secret; писати маніфест і користуватися kubectl.

Віртуалізація#

Принцип «один застосунок — один фізичний сервер» означає: багато серверів, ліцензії ОС для кожного і низьке завантаження кожної машини. Розділяй і володарюй — розв'язок дає віртуалізація.

Визначення

Гіпервізор (VMM, virtual machine monitor) — ПЗ, прошивка або залізо, що створює і запускає віртуальні машини. Комп'ютер із гіпервізором — host (хост), кожна ВМ — guest (гість). Приклади: KVM, Xen, VMware, Oracle VirtualBox.

Але для клієнта цінність — застосунок, а не ОС. У кожній ВМ своя повна ОС, яка споживає багато CPU, RAM і диска: OS ≠ business value.

ВМ vs контейнер#

Віртуальна машинаКонтейнер

ЯдроВласне в кожній ВМСпільне ядро хоста
РесурсиБагато CPU/RAM/диска на ОСМенше CPU, RAM і диска
ІзоляціяСильнішаДостатня для більшості задач, але слабша

Конфлікт бібліотек: два застосунки на одному сервері потребують різних версій однієї бібліотеки — у спільній ОС конфлікт. У контейнерах кожен застосунок несе свій user space зі своїми версіями.

Як працюють контейнери: механізми ядра#

Контейнери — це можливість Unix-подібних ОС, а не винахід Docker. Docker лише зручна обгортка над функціями ядра.

NamespacesІзоляція «що бачить процес»

PID — свої процеси (усередині свій PID 1), MNT — своя файлова система, NET — своя мережа, USER — свої користувачі й привілеї.

Control groups (cgroups)Обмеження ресурсів

Групують процеси і ставлять ліміти: скільки CPU, RAM, I/O може взяти контейнер.

CapabilitiesДрібні привілеї

Замість «усе або нічого» root — окремі дозволи (напр. лише прив'язка до порту < 1024).

Формула зі слайдів

cgroups + namespaces + image = Docker-контейнер. Namespaces дають ізоляцію, cgroups — ліміти, образ — файлову систему із застосунком.

Docker: архітектура і терміни#

Docker — набір PaaS-продуктів, що використовують віртуалізацію рівня ОС для постачання ПЗ в пакетах — контейнерах. Docker Engine — клієнт-серверний застосунок: CLI-клієнт спілкується з демоном dockerd через REST API.

ImageОбраз

Шаблон застосунку: набір файлів і параметрів. Конструкція часу збирання (build time). Не файлова система і не віртуальний диск — по суті tar-архів шарів з ієрархією.

ContainerКонтейнер

Запущений екземпляр образу — ізольований процес на Docker-хості зі спільним ядром. Конструкція часу виконання (runtime).

RegistryРеєстр

Мережеве сховище образів, приватне чи публічне. Найбільший публічний — Docker Hub.

DockerfileРецепт образу

Текстовий файл з інструкціями, які Docker виконує, щоб зібрати образ.

Шари образу

Образ складається з шарів: кожна інструкція Dockerfile — окремий шар, усі шари образу лише для читання. Коли запускається контейнер, зверху додається тонкий записуваний шар — зміни контейнера живуть лише в ньому і зникають разом із контейнером. Спільні шари (напр. базовий python) зберігаються один раз для всіх образів.

Docker зсередини: від команди до процесу, образи, теги і кеш#

Що відбувається після docker run nginx

docker (CLI) ──REST API──► dockerd (Docker daemon) ──gRPC──► containerd ──► containerd-shim ──► runc
   ваша команда              керує образами, мережами,       керує життєвим          створює процес
                             томами; тягне образи з реєстру   циклом контейнерів      з namespaces і cgroups
  1. CLI надсилає запит демону через сокет /var/run/docker.sock. Хто має доступ до цього сокета (група docker), фактично має права root на хості.
  2. Демон шукає образ nginx:latest локально; якщо немає — завантажує шари з реєстру (Docker Hub за замовчуванням).
  3. Поверх шарів образу (лише для читання) створюється тонкий записуваний шар контейнера.
  4. containerd і runc створюють процес у нових namespaces (свої PID, мережа, файлова система) з обмеженнями cgroups.
  5. Docker підключає контейнер до мережі bridge, видає IP (172.17.0.x) і запускає команду з CMD/ENTRYPOINT образу.

Формат образів і запуску стандартизований OCI (Open Container Initiative). Тому образ, зібраний Docker, запускають і Podman, і Kubernetes (через containerd або CRI-O) — без Docker на вузлі.

Образ і контейнер: клас і об'єкт

Образ (image)

  • шаблон лише для читання: шари файлової системи + метадані (CMD, ENV, порти)
  • один образ → багато контейнерів
  • зберігається в реєстрі, має тег і digest
  • створюється docker build або docker pull

Контейнер (container)

  • запущений (або зупинений) екземпляр образу з власним записуваним шаром
  • має стан: running, exited…
  • зміни в ньому зникають при видаленні, якщо не винесені в томи
  • створюється docker run / docker create

Життєвий цикл контейнера

created ──docker start──► running ──docker pause──► paused ──docker unpause──► running
                            │
                            │ процес завершився сам, або docker stop
                            │ (SIGTERM, через 10 с — SIGKILL), або docker kill (SIGKILL одразу)
                            ▼
                          exited ──docker start / restart──► running
                            │
                            └──docker rm──► контейнер видалено разом із записуваним шаром

docker run = docker create + docker start (+ підключення до виводу, якщо без -d)
Політика перезапуску (--restart)Поведінка
no (за замовчуванням)не перезапускати
on-failure[:5]перезапускати лише при ненульовому коді виходу, до 5 спроб
alwaysперезапускати завжди, включно з рестартом демона/сервера
unless-stoppedяк always, але не піднімати, якщо зупинили вручну

Теги і digest: як точно вказати версію

ghcr.io/acme/shop:2.14.0
└──┬──┘ └──┬─┘└┬─┘ └──┬─┘
 реєстр  власник ім'я   тег (рухома мітка — її можна перевісити на інший образ)

ghcr.io/acme/shop@sha256:9f1c2e…   ← digest: хеш вмісту, змінити неможливо
  • Без реєстру в імені — Docker Hub (nginx = docker.io/library/nginx:latest).
  • latest — лише тег за замовчуванням, а не «найновіша версія». Його можуть не оновлювати роками.
  • У production посилаються на конкретну версію або digest, щоб два розгортання гарантовано отримали той самий образ.

Шари і кеш збірки в дії

FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
CMD ["python", "app.py"]
$ docker build -t shop:1 .        # друга збірка після зміни лише app.py
 => [1/5] FROM python:3.12-slim                                  CACHED
 => [2/5] WORKDIR /app                                           CACHED
 => [3/5] COPY requirements.txt .                                CACHED
 => [4/5] RUN pip install --no-cache-dir -r requirements.txt     CACHED   ← залежності не перевстановлюються
 => [5/5] COPY . .                                               0.1s     ← змінився лише цей шар

Правило кешу: якщо змінився шар N, усі шари після нього перебудовуються. Тому рідко змінюване (залежності) копіюють раніше, а код, що змінюється з кожним комітом, — пізніше. Якби COPY . . стояв перед pip install, кожна правка коду запускала б повне встановлення залежностей.

$ docker history shop:1
IMAGE          CREATED BY                                      SIZE
a1b2c3d4e5f6   CMD ["python" "app.py"]                         0B
<missing>      COPY . .                                        48kB
<missing>      RUN pip install --no-cache-dir -r requirem…     21MB
<missing>      COPY requirements.txt .                         120B
<missing>      WORKDIR /app                                    0B
<missing>      (шари базового образу python:3.12-slim)         ~120MB

Інструкції RUN, COPY, ADD створюють шари з файлами; CMD, ENV, EXPOSE, WORKDIR — лише метадані (0 байт).

Dockerfile#

Dockerfile схожий на shell-скрипт із ключовими словами: розширює базовий образ (FROM) і дає новий образ. Формат: # коментар і ІНСТРУКЦІЯ аргументи. docker build збирає образ з Dockerfile і контексту — набору файлів за шляхом (PATH) або URL Git-репозиторію.

ІнструкціяПризначення
FROMБазовий образ (перша інструкція)
RUNКрок збирання: виконати команду і зафіксувати результат у новому шарі (встановити пакети). Може бути багато
COPY / ADDСкопіювати файли з контексту в образ (ADD вміє ще URL і розпакування архівів)
WORKDIRРобочий каталог для наступних інструкцій
ENV, LABELЗмінні оточення, метадані
EXPOSEДокументує, який порт слухає контейнер (саме по собі порт не публікує)
CMDКоманда за замовчуванням при старті контейнера. Діє лише остання; перевизначається: docker run image інша_команда
ENTRYPOINTГоловна команда контейнера; CMD тоді стає її аргументами за замовчуванням
VOLUME, HEALTHCHECK, USER…Томи для даних, перевірка здоров'я, користувач тощо

Dockerfile детально: CMD vs ENTRYPOINT, багатоетапна збірка, найкращі практики#

Форми shell і exec

ФормаЗаписЯк запускається
exec (рекомендована)CMD ["python", "app.py"]програма стає процесом з PID 1 і отримує сигнали (docker stop → SIGTERM) напряму
shellCMD python app.pyзагортається в /bin/sh -c "python app.py"; PID 1 — оболонка, яка може не передати SIGTERM застосунку, і контейнер зупиниться лише через 10 с примусово

CMD vs ENTRYPOINT: що виконається

Dockerfiledocker run imgdocker run img --help
CMD ["nginx", "-g", "daemon off;"]nginx -g daemon off;--help (CMD повністю замінено, найімовірніше помилка)
ENTRYPOINT ["curl"]curlcurl --help
ENTRYPOINT ["curl"] + CMD ["https://example.com"]curl https://example.comcurl --help (CMD — аргументи за замовчуванням, їх замінено)

Правило: ENTRYPOINT — «що це за програма», CMD — «аргументи за замовчуванням». ENTRYPOINT перевизначається лише явно: docker run --entrypoint sh img.

Інші пари, які плутають

  • ARG vs ENV: ARG VERSION=1.2 існує лише під час збирання (docker build --build-arg VERSION=1.3); ENV APP_ENV=prod зберігається в образі і доступна в запущеному контейнері (перевизначається docker run -e).
  • COPY vs ADD: використовуйте COPY; ADD додатково розпаковує локальні tar-архіви і завантажує URL, що робить збірку менш передбачуваною.
  • RUN vs CMD: RUN виконується під час збирання і фіксує результат у шарі; CMD — під час запуску контейнера.
  • EXPOSE vs -p: EXPOSE 8080 лише документує порт; відкриває його назовні лише docker run -p 8282:8080.

Багатоетапна збірка (multi-stage build)

Інструменти збирання (компілятор, dev-залежності) не потрібні в production-образі. Багатоетапна збірка використовує кілька FROM: у першому етапі збирають, у фінальний копіюють лише результат.

# ---- етап 1: збірка ----
FROM node:20 AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci                           # залежності — окремим шаром, кешується
COPY . .
RUN npm run build                    # результат у /app/dist

# ---- етап 2: лише статичні файли за nginx ----
FROM nginx:1.27-alpine
COPY --from=build /app/dist /usr/share/nginx/html
EXPOSE 80
HEALTHCHECK CMD wget -qO- http://localhost/ || exit 1

Образ node:20 важить понад 1 ГБ, а фінальний на nginx:alpine — десятки мегабайт: менше завантажувати, менше вразливостей.

Найкращі практики

  1. Невеликий базовий образ з фіксованою версією: python:3.12-slim, alpine:3.20, distroless. Тег latest змінюється без попередження.
  2. Порядок шарів: те, що рідко змінюється (залежності), — вище; код — нижче.
  3. Об'єднуйте команди і прибирайте кеш у тому самому RUN: RUN apt-get update && apt-get install -y --no-install-recommends curl && rm -rf /var/lib/apt/lists/*. Файл, видалений у наступному шарі, однаково лишається в попередньому.
  4. Не root: RUN useradd -r app і USER app.
  5. Секрети не в образ: жодних паролів в ENV чи скопійованих файлах — їх видно в docker history. Передавайте під час запуску (змінні оточення, Docker secrets, Kubernetes Secrets).
  6. .dockerignore: .git, node_modules, .env, логи — менший контекст і швидша збірка.
  7. Один процес на контейнер: вебсервер і БД — в окремих контейнерах.

Теги, реєстри, публікація

docker build -t myapp:1.4.2 .                    # зібрати з тегом
docker tag myapp:1.4.2 ghcr.io/anna/myapp:1.4.2  # додати тег з адресою реєстру
docker login ghcr.io                             # автентифікація (Docker Hub — просто docker login)
docker push ghcr.io/anna/myapp:1.4.2             # опублікувати
docker pull nginx@sha256:4c0fdaa8b6341bfdeca5f18f7837462c80cff90527ee35ef185571e1c327beac   # за digest — незмінний образ
docker history myapp:1.4.2                       # шари і команди, що їх створили
docker image inspect myapp:1.4.2                 # метадані: ENV, CMD, ENTRYPOINT, шари

Повне ім'я образу: [реєстр/][простір/]ім'я[:тег|@digest]. Без реєстру — Docker Hub, без тегу — latest. Тег можна перепризначити на інший образ, digest (sha256:…) — ні.

Практичний кейс: Python-вебсервер у контейнері#

Файли з архіву лекції server.zip:

server.py

#!/usr/bin/env python3
import http.server
import socketserver

handler = http.server.SimpleHTTPRequestHandler
with socketserver.TCPServer(("", 1234), handler) as httpd:
    httpd.serve_forever()

Dockerfile

FROM python:latest
ADD server.py /server/
ADD index.html /server/
WORKDIR /server/
CMD ["python", "./server.py"]

docker run --name myserver -d -p 1234:1234 serverimage      # -d у фоні, -p ХОСТ:КОНТЕЙНЕР
curl http://localhost:1234                                  # Hello world!

Пастка «localhost» у контейнері

Усередині контейнера localhost — це сам контейнер, а не хост і не інший контейнер. Застосунок у контейнері web має підключатися до бази як db:5432 (ім'я сервісу), а не localhost:5432. До сервісів на хості з контейнера звертаються через host.docker.internal (Docker Desktop; у Linux — з --add-host=host.docker.internal:host-gateway).

Типи гіпервізорів, шари, томи, Compose і Kubernetes#

Гіпервізор типу 1 (bare-metal)

Ставиться прямо на залізо замість ОС. Для дата-центрів і хмар. VMware ESXi, Microsoft Hyper-V, Xen, KVM.

Гіпервізор типу 2 (hosted)

Звичайна програма всередині ОС. Для навчання і розробки. Oracle VirtualBox, VMware Workstation.

Шари образу і кеш збірки

Кожна інструкція Dockerfile, що змінює файлову систему (RUN, COPY, ADD), створює шар (layer). Шари лише для читання, кешуються і спільні між образами. Якщо шар змінився, усі шари після нього збираються наново — тому рідко змінні кроки (встановлення залежностей) ставлять вище, а COPY . . з кодом — нижче. Файл .dockerignore не пускає в образ зайве (.git, node_modules).

Томи: дані поза контейнером

Контейнер ефемерний: після docker rm усе, що він записав у себе, зникає. Дані БД зберігають у volume: docker run -v pgdata:/var/lib/postgresql/data postgres (іменований том) або -v /home/me/site:/usr/share/nginx/html (bind mount — каталог хоста).

docker compose up -d — підняти все у фоні, docker compose logs — логи, docker compose down — зупинити й видалити контейнери. Сервіси бачать одне одного за іменами (web звертається до db:3306).

Kubernetes коротко

Kubernetes (K8s) — оркестратор контейнерів: запускає їх на кластері з багатьох машин, перезапускає впалі, масштабує і оновлює без простою. Кластер = control plane (керування) + worker nodes (де працюють контейнери).

PodПод

Найменша одиниця: один або кілька контейнерів зі спільною мережею.

DeploymentРозгортання

Скільки реплік поду тримати; плавне оновлення (rolling update).

ServiceСервіс

Стабільна адреса і балансування між подами.

Керують через kubectl: kubectl apply -f app.yaml, kubectl get pods. Маніфести — декларативний YAML.

  name: web

  replicas: 3                       # бажаний стан: три поди

    matchLabels: { app: web }

    metadata:
      labels: { app: web }
    spec:
      containers:
        - name: web
          image: ghcr.io/anna/myapp:1.4.2
          ports: [{ containerPort: 8080 }]
          resources:
            requests: { cpu: 100m, memory: 128Mi }
            limits:   { memory: 256Mi }
          readinessProbe:           # под отримує трафік лише коли готовий

          livenessProbe:            # завис — kubelet перезапустить контейнер
            httpGet: { path: /health, port: 8080 }
---
apiVersion: v1
kind: Service
metadata:
  name: web
spec:
  selector: { app: web }            # трафік на поди з міткою app=web
  ports: [{ port: 80, targetPort: 8080 }]
  type: ClusterIP

Readiness, liveness, startup probes

ProbeПитанняЩо буде, якщо не пройшла
readinessProbe«чи готовий под приймати трафік?»под прибирається з Service (трафік не йде), але не перезапускається
livenessProbe«чи живий процес, чи не завис?»kubelet перезапускає контейнер
startupProbe«чи завершився повільний старт?»поки не пройшла, liveness і readiness не перевіряються

Автомасштабування

kubectl autoscale deploy/web --cpu-percent=70 --min=2 --max=10   # HorizontalPodAutoscaler
kubectl get hpa                                                   # поточне навантаження і кількість реплік

HPA додає поди, коли середнє використання CPU перевищує 70 % від requests. Без заданих resources.requests HPA за CPU не працює. Нових вузлів, якщо подам не вистачає місця, додає окремий Cluster Autoscaler.

Типові помилки#

EXPOSE 80 у Dockerfile відкриває порт назовні.
EXPOSE лише документує порт. Назовні його публікує docker run -p 8080:80.
Видалити файл у наступному RUN — і образ стане меншим.
Попередній шар уже містить файл. Чистити кеш треба в тому самому RUN або використовувати multi-stage build.
Пароль БД можна покласти в ENV у Dockerfile.
Його видно в docker history та inspect. Секрети передають під час запуску.
Контейнер з кодом виходу 137 «впав через помилку в коді».
137 = 128 + 9: процес вбито SIGKILL, найчастіше через перевищення ліміту пам'яті (OOM).
Service в Kubernetes — це контейнер.
Service — стабільна адреса і балансування для набору подів, обраних за мітками.
Дані, записані всередині контейнера, переживуть його видалення.
Контейнер ефемерний. Усе важливе — у volume або bind mount.
Образ і контейнер — одне й те саме.
Образ — незмінний шаблон (build time), контейнер — його запущений екземпляр (runtime). З одного образу можна запустити багато контейнерів.
EXPOSE 1234 робить сервіс доступним ззовні.
EXPOSE лише документує порт. Публікує його docker run -p ХОСТ:КОНТЕЙНЕР.
Запускати сервер через RUN python server.py.
RUN виконується під час збирання образу. Команда старту контейнера — CMD або ENTRYPOINT (тому на слайді RUN закоментовано).
Зберігати дані БД усередині контейнера.
Записуваний шар зникає з контейнером. Дані виносять у томи (-v/VOLUME).
Контейнер = «легка ВМ» з власним ядром.
Контейнери ділять ядро хоста; ізоляцію дають namespaces, а ліміти — cgroups.
