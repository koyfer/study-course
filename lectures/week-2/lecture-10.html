Системи контролю версій: Git, гілки, Git Flow і pull request

Git — фундамент усієї автоматизації: код застосунку, Dockerfile, Terraform-конфігурації та CI-пайплайни живуть у репозиторії. Розбираємо, як Git зберігає зміни і як команда працює з гілками та pull request-ами.

Чого ви навчитесь#

  • Пояснити, яку проблему розв'язує VCS, і порівняти моделі lock-modify-unlock та copy-modify-merge.
  • Розрізняти централізовані (SVN) і розподілені (Git) системи.
  • Описати три зони Git — робочий каталог, індекс, репозиторій — і рух змін між ними.
  • Користуватися базовими командами, розв'язувати конфлікти, відкочувати зміни (reset vs revert).
  • Пояснити Git Flow, GitHub Flow і процес pull request.
  • Пояснити, як Git зберігає дані (blob, tree, commit), що таке гілка, HEAD і detached HEAD.
  • Знати стани файлів, різницю fetch і pull, upstream, і як скасувати будь-яку зміну (restore, reset, revert, reflog).
  • Порівняти Git Flow, GitHub Flow і trunk-based; писати повідомлення комітів за Conventional Commits; налаштувати захист main, hooks і теги.
  • Налаштувати Git і SSH-доступ до GitHub, писати .gitignore.
  • Розрізняти fast-forward, тристороннє злиття, rebase і squash на графах; виходити з 12 типових проблемних ситуацій.

Навіщо контроль версій#

Звичайний файловий сервер дає спільне сховище, але не пам'ятає історії. Репозиторій — особливий файловий сервер, що пам'ятає кожну зміну: кожного файла і навіть структури каталогів. Клієнт зазвичай бачить останню версію, але може переглянути будь-який попередній стан.

Інструменти в історичному порядку: CVS (1986, клієнт-сервер, розвиток зупинено 2008), Apache Subversion (SVN) (2000, наступник CVS; клієнти TortoiseSVN, RabbitVCS), Microsoft VSS (для малих проєктів, підтримку завершено 2016), TFS (Team Foundation Server у складі Visual Studio Team System), і нарешті Git (2005). За словами інструктора, SVN зараз переважно трапляється в історії старих проєктів — основний інструмент Git.

Проблема одночасного редагування

Гаррі і Саллі одночасно редагують один файл. Гаррі зберігає першим, Саллі — за хвилину, і непомітно перезаписує зміни Гаррі. Вони не втрачені назавжди (система пам'ятає історію), але в останній версії їх немає.

Lock-Modify-Unlock

  • Щоб редагувати, файл треба заблокувати; інші лише читають.
  • Конфліктів немає, але люди чекають.
  • Гаррі забув зняти блокування і пішов у відпустку — Саллі потрібен адміністратор.

Copy-Modify-Merge

  • Кожен працює зі своєю робочою копією, паралельно.
  • Наприкінці копії зливаються (merge); VCS допомагає, але відповідає людина.
  • Якщо зміни перетинаються — конфлікт, який розв'язує людина. На практиці конфлікти рідкісні й дешевші за очікування блокувань.

Жодна система не виявить семантичні конфлікти (код зливається, але логіка ламається) — тому потрібні комунікація, рев'ю і тести.

Централізовані vs розподілені VCS

Git: старт#

Git — розподілена система контролю версій з акцентом на швидкість, цілісність даних і нелінійну розробку (багато гілок). Створена Лінусом Торвальдсом у 2005 для розробки ядра Linux.

sudo apt install git           # Debian/Ubuntu (Windows: git-scm.com/download/win)
git config --global user.name  "Ivan Petrenko"     # автор комітів
git config --global user.email "ivan@example.com"
git config --list               # перевірити налаштування
git help commit                 # довідка: також git commit --help

.gitignore — шаблони файлів, які Git не відстежує: порожні рядки і рядки з # ігноруються, / в кінці — каталог, ! — виняток.

*.[oa]          # об'єктні файли й архіви
/target/        # каталог target у корені
doc/*.txt       # doc/notes.txt, але не doc/info/arch.txt
doc/**/*.txt    # усі .txt у doc на будь-якій глибині
.env            # секрети — ніколи не в Git

Доступ до GitHub по SSH

Три зони Git і рух змін#

Базовий цикл

git init                                  # новий репозиторій у поточному каталозі
git clone https://github.com/user/repo.git   # або копія існуючого
git remote add origin <url>               # прив'язати віддалений репо
git remote -v                             # список remotes

git status                                # що змінено / в індексі
git add readme.txt                        # додати файл в індекс (git add . — усі)
git diff --staged                         # що піде в коміт
git commit -m "Add readme"                # зафіксувати
git commit --amend -m "Better message"    # виправити ОСТАННІЙ коміт (до push!)
git push origin main                      # відправити гілку main
git pull origin main                      # забрати й злити зміни з сервера

git log -3 / git log -p -2 / git log --since=2.weeks
git reflog                                # журнал переміщень HEAD — рятує «втрачені» коміти
git rm --cached file                      # прибрати з індексу, залишити на диску
git mv old new                            # перейменувати

Відкат змін: reset vs revert

КомандаРобочий каталогІндексЛокальний репо (HEAD)
git reset --soft f314b2без змінбез змінпереноситься
git reset f314b2 (mixed)без зміноновлюєтьсяпереноситься
git reset --hard f314b2перезаписуєтьсяоновлюєтьсяпереноситься

reset переписує історію — безпечно лише для локальних, ще не надісланих комітів. Для вже опублікованих змін використовують git revert <sha>: він створює новий коміт, що скасовує старий, і нікому не ламає історію. git push -f (примусово) на спільну гілку — крайній захід.

Як Git влаштований усередині, стани файлів і скасування змін#

Об'єкти, хеші і посилання

Git зберігає не «різниці», а знімки (snapshots) проєкту. Усе лежить у каталозі .git/objects як об'єкти, ідентифіковані хешем SHA-1 (40 hex-символів; нові репозиторії можуть використовувати SHA-256):

blobВміст файла

Лише байти, без імені. Однакові файли зберігаються один раз.

treeКаталог

Список імен і посилань на blob-и та інші tree.

commitКоміт

Посилання на кореневий tree, батьківський коміт(и), автор, дата, повідомлення.

tagАнотований тег

Іменована позначка на коміт з автором і повідомленням.

  • Гілка — лише файл з хешем останнього коміту (.git/refs/heads/main). Тому гілки в Git створюються миттєво.
  • HEAD — вказівник на поточну гілку (або напряму на коміт). cat .git/HEAD → ref: refs/heads/main.
  • Detached HEAD — HEAD вказує на коміт, а не на гілку (після git checkout a1b2c3d або тегу). Нові коміти тут не належатимуть жодній гілці; щоб зберегти — git switch -c new-branch.
  • Хеш коміту залежить від усього вмісту і батьків, тому зміна будь-якого старого коміту змінює хеші всіх наступних — так Git гарантує цілісність історії.

Стани файлів

СтанЗначенняЯк перейти далі

fetch vs pull, remote-tracking гілки

  • git fetch завантажує нові коміти з сервера в remote-tracking гілки (origin/main), але не змінює ваші локальні гілки і робочий каталог. Безпечно в будь-який момент.
  • git pull = git fetch + git merge origin/main (або --rebase) у поточну гілку.
  • git push -u origin feature/login — перший push нової гілки; -u запам'ятовує зв'язок (upstream), далі досить git push.
  • git branch -vv покаже, на скільки комітів ви попереду/позаду сервера.

Як скасувати що завгодно

СитуаціяКоманда
Відкинути незбережені зміни у файліgit restore app.py (раніше git checkout -- app.py)
Прибрати файл з індексу, залишивши зміниgit restore --staged app.py (раніше git reset HEAD app.py)
Змінити повідомлення або додати файл до останнього коміту (ще не запушеного)git add forgotten.txt && git commit --amend
Скасувати останній коміт, зберігши зміниgit reset --soft HEAD~1
Повністю викинути останній локальний коміт і зміниgit reset --hard HEAD~1 (обережно)
Скасувати вже опублікований комітgit revert <sha> — новий коміт-«антидот»
Повернути випадково видалену гілку або коміт після resetgit reflog → знайти хеш → git switch -c rescue <sha>

HEAD~1 — батько поточного коміту, HEAD~3 — на три коміти назад.

Гілки і стратегії#

git branch testing            # створити гілку
git checkout testing          # перейти (git checkout -b testing — створити й перейти)
# … коміти …
git checkout main
git merge testing             # злити testing у поточну (main)
git branch -d testing         # видалити локально
git push origin :testing      # видалити на сервері (або --delete testing)

Git Flow (Вінсент Дріссен, 2010)

  • main (master) — production-код; develop — передрелізний код. Обидві існують завжди.
  • feature-*: від develop → назад у develop.
  • release-*: від develop → у main і develop (дрібні фікси, метадані релізу).
  • hotfix-*: від main → у main і develop (терміново виправити production).

GitHub Flow (GitHub, 2011)

  • Усе в main — завжди готове до деплою.
  • Нова робота — у гілці від main з описовою назвою (new-oauth2-scopes).
  • Регулярно комітимо і пушимо гілку на сервер.
  • Потрібен фідбек або готово — відкриваємо pull request.
  • Після рев'ю і схвалення — merge у main і одразу деплой.

Злиття наочно: fast-forward, тристороннє злиття, rebase, squash#

Fast-forward: гілку просто «пересувають»

До:   main:    A───B
                     \
      feature:        C───D

git switch main && git merge feature

Після: main, feature:  A───B───C───D       ← нового коміту немає, main лише перемістився на D

Можливе, коли в main не з'явилось нових комітів після відгалуження. Щоб усе одно створити merge-коміт (і бачити в історії, що була окрема гілка), використовують git merge --no-ff feature.

Тристороннє злиття (three-way merge)

До:   main:    A───B───E               ← у main з'явився коміт E
                     \
      feature:        C───D

git switch main && git merge feature

Після: main:   A───B───E───M          ← M — merge-коміт з ДВОМА батьками (E і D)
                     \     /
                      C───D

«Три сторони» — спільний предок B, вершина main E і вершина feature D. Git порівнює обидві гілки з предком: якщо змінено різні місця — зливає автоматично, якщо той самий рядок — конфлікт.

Rebase: переписати свої коміти поверх свіжої main

До:   main:    A───B───E
                     \
      feature:        C───D

git switch feature && git rebase main

Після: main:    A───B───E
                         \
       feature:           C'───D'      ← нові коміти з НОВИМИ хешами (C' ≠ C)

git switch main && git merge feature    → тепер fast-forward, історія лінійна
Золоте правило rebase

Не робіть rebase комітів, які вже є на сервері і з якими працюють інші. Rebase створює нові коміти; у колег лишаться старі, і їхні гілки розійдуться з вашими. Свою локальну гілку перед PR — можна; після такого rebase потрібен git push --force-with-lease (безпечніший за --force: не перезапише чужі нові коміти).

Interactive rebase: прибрати «шум» перед PR

$ git log --oneline
f3e1a2c fix typo again
9b8c7d6 fix typo
4a5b6c7 add stock badge
1d2e3f4 (origin/main) ...

$ git rebase -i HEAD~3          # відкриється редактор:

# команди: pick — залишити, reword — змінити повідомлення, squash/fixup — злити з попереднім,
#          drop — видалити, edit — зупинитись для змін

Результат: один коміт «add stock badge» з усіма змінами

Робіть це лише з комітами, які ще не потрапили в спільну гілку.

Pull request: командна робота#

Pull request (PR) повідомляє команду про зміни, які ви запушили в гілку. У PR обговорюють і переглядають код, додають нові коміти — і лише потім зливають у базову гілку. Це ключовий результат курсу: «репозиторій на GitHub з pull request-ами та рев'ю».

  1. Власник репозиторію запрошує учасників (collaborators) і налаштовує правила захисту гілки: зміни в main лише через PR, обов'язкове схвалення.
  2. Учасник клонує репозиторій і створює нову гілку.
  3. Змінює код → commit → push гілки.
  4. Відкриває pull request і чекає рев'ю.
  5. Після схвалення зміни зливаються; гілку зазвичай видаляє той, хто зробив merge.
Секрети в репозиторії

З чату лекції: якщо пароль чи токен випадково потрапив у Git, мало видалити його з історії — секрет треба негайно змінити (відкликати), бо копії репозиторію вже могли розійтися. Великі бінарні файли в Git не зберігають (для цього є Git LFS).

Командні практики: моделі гілок, коміти, захист main#

Три популярні моделі гілок

МодельЯк працюєКоли підходить
Git Flowдовгі гілки main і develop, плюс feature/*, release/*, hotfix/*продукти з плановими версіями (мобільні застосунки, коробкове ПЗ)
GitHub Flowодна головна гілка main, яку завжди можна розгорнути; кожна зміна — коротка гілка + pull request + деплой після злиттявебсервіси з частим деплоєм
Trunk-based developmentусі зливають маленькі зміни в main щонайменше щодня; незавершене ховають за feature flagsкоманди з розвиненим CI/CD; рекомендується дослідженнями DORA

Гарне повідомлення коміту

fix(auth): reject expired JWT tokens          ← заголовок до ~50 символів, наказовий спосіб

Tokens were validated only by signature, so expired tokens
were still accepted. Check the exp claim and return 401.

Closes #142                                     ← посилання на задачу

Специфікація Conventional Commits задає префікси: feat: (нова функція), fix: (виправлення), docs:, refactor:, test:, chore:, ci:; BREAKING CHANGE — несумісна зміна. З таких комітів інструменти автоматично генерують changelog і наступну версію за SemVer. Один коміт — одна логічна зміна: так його легше переглянути і, якщо треба, відкотити через revert.

Захист головної гілки

  • Protected branch: заборонити прямий push і push --force у main.
  • Обов'язковий pull request з мінімум одним схваленням (approve) і зеленими перевірками CI (required status checks).
  • CODEOWNERS — файл, що автоматично призначає рецензентів для певних каталогів (/infra/ @devops-team).
  • Підписані коміти (GPG/SSH) — підтвердження авторства.

Хуки і перевірки до коміту

Git hooks — скрипти в .git/hooks/, що запускаються на події: pre-commit (перед комітом: лінтер, форматування, пошук секретів), commit-msg (перевірити формат повідомлення), pre-push (тести). Фреймворк pre-commit дає змогу зберігати набір перевірок у репозиторії (.pre-commit-config.yaml), щоб у всіх вони були однакові.

Якщо в Git потрапив секрет

Видалення файла новим комітом не допоможе: секрет залишається в історії, і його вже могли скопіювати. Порядок дій: негайно відкликати і замінити ключ чи пароль (rotate), потім за потреби почистити історію (git filter-repo, BFG) і змусити всіх перевзяти репозиторій. Запобігання: .gitignore для .env, сканери секретів у pre-commit і CI (gitleaks), GitHub Secret Scanning.

Теги і релізи

git tag -a v1.4.2 -m "Release 1.4.2"     # анотований тег (з автором і повідомленням)
git push origin v1.4.2                   # теги не пушаться автоматично; всі — git push --tags
git describe --tags                      # v1.4.2-3-gabc1234: 3 коміти після тегу
git checkout v1.4.2                      # перейти на версію (detached HEAD)

merge vs rebase, stash і розв'язання конфлікту#

git merge feature

  • Створює merge-коміт з двома батьками.
  • Історія чесна, але розгалужена.
  • Безпечно для спільних гілок.

git rebase main

  • Переписує ваші коміти поверх main (нові хеші).
  • Історія лінійна, без merge-комітів.
  • Не робіть rebase гілок, які вже запушені й використовуються іншими.

Конфлікт крок за кроком

  1. git merge feature → CONFLICT (content): Merge conflict in app.py.
  2. У файлі з'являються маркери: <<<<<<< HEAD (ваша версія) … ======= … >>>>>>> feature (версія гілки).
  3. Залишаєте потрібний код і видаляєте маркери.
  4. git add app.py — позначити конфлікт розв'язаним, потім git commit (або git merge --continue). Передумали — git merge --abort.

Ще корисні команди

git stash                   # сховати незакомічені зміни (щоб перейти на іншу гілку)
git stash pop               # повернути їх
git switch -c feature/login # створити гілку й перейти (= git checkout -b)
git log --oneline --graph   # компактна історія з гілками
git diff                    # незаіндексовані зміни; git diff --staged — проіндексовані
git cherry-pick a1b2c3d     # перенести один коміт на поточну гілку
git tag v1.0                # позначити реліз

12 реальних ситуацій з Git і як із них вийти#

1. Закомітили в main замість нової гілки (ще не пушили)

git switch -c feature/stock-badge      # нова гілка вказує на поточний коміт — робота врятована
git switch main
git reset --hard origin/main           # повернути локальну main до стану сервера

2. Забули додати файл в останній коміт або помилились у повідомленні

git add forgotten.py
git commit --amend -m "Add stock badge with tests"   # замінює останній коміт; лише якщо ще не запушено

3. Треба скасувати коміт, який уже в main на сервері

git log --oneline -5                   # знайти хеш, напр. 4a5b6c7
git revert 4a5b6c7                     # новий коміт, що робить протилежні зміни; історія не переписується
git push

Не reset + push --force: колеги вже мають цей коміт, і їхні репозиторії розійдуться з сервером.

4. Випадково закомітили пароль і запушили

  1. Негайно змінити (відкликати) секрет — він уже скомпрометований, навіть якщо репозиторій приватний.
  2. Прибрати файл з відстеження: git rm --cached .env, додати в .gitignore, закомітити.
  3. За потреби очистити історію (git filter-repo або BFG Repo-Cleaner) і зробити force push — але копії, форки й кеші вже могли зберегти секрет, тому пункт 1 головний.

5. git pull закінчився конфліктом

git status                             # both modified: app.py
# відкрити app.py, обрати потрібний код, видалити маркери <<<<<<< ======= >>>>>>>
git add app.py
git commit                             # завершити злиття (при pull --rebase: git rebase --continue)
# передумали зливати:
git merge --abort                      # або git rebase --abort

6. Повідомлення «You are in 'detached HEAD' state»

git switch -c fix/from-old-version     # зберегти нові коміти в гілці, якщо вони потрібні
git switch main                        # або просто повернутися на гілку

HEAD вказує на конкретний коміт, а не на гілку (наприклад, після git checkout v1.2). Коміти, зроблені в такому стані без створення гілки, згодом знайде лише git reflog.

7. Знайти коміт, після якого зламались тести

git bisect start
git bisect bad                         # поточна версія зламана
git bisect good v2.13.0                # ця версія працювала
# Git переключає на коміт посередині; перевіряєте і кажете:
git bisect good   # або   git bisect bad
# ... кілька кроків бінарного пошуку ...
# "a1b2c3d is the first bad commit"
git bisect reset
# автоматично: git bisect run pytest tests/test_cart.py

Для 1000 комітів між хорошою і поганою версіями потрібно близько 10 перевірок (2¹⁰ = 1024).

8. Хто і коли змінив цей рядок

git blame -L 40,55 app/cart.py         # автор і коміт для кожного рядка 40–55
git log -p -S "discount_rate" -- app/  # коміти, що додали або прибрали цей текст
git log --follow -- app/cart.py        # історія файла навіть після перейменувань

9. Оновити свою гілку змінами з main

git switch feature/stock-badge
git fetch origin
git rebase origin/main                 # або git merge origin/main, якщо гілка спільна
git push --force-with-lease            # після rebase — лише для СВОЄЇ гілки

10. Перейменувати гілку і видалити стару на сервері

git branch -m feature/badge feature/stock-badge
git push -u origin feature/stock-badge
git push origin --delete feature/badge
git fetch --prune                      # прибрати локальні посилання на видалені на сервері гілки

11. Оновити свій fork змінами з оригінального репозиторію

git remote add upstream https://github.com/original/project.git
git fetch upstream
git switch main
git merge upstream/main                # або rebase
git push origin main

12. Потрібно терміново переключитись, а робота не завершена

git stash push -m "WIP: badge styles"  # сховати незакомічені зміни
git switch hotfix/payment
# ... виправили, закомітили ...
git switch feature/stock-badge
git stash list                         # stash@{0}: On feature/stock-badge: WIP: badge styles
git stash pop                          # повернути і видалити зі stash (apply — повернути, але залишити)

Невідстежувані (нові) файли git stash за замовчуванням не ховає — для них git stash -u.

Типові помилки#

git fetch оновлює мою гілку і файли.
fetch лише завантажує коміти в origin/*. Злиття у вашу гілку робить merge або pull.
Секрет, який потрапив у коміт, досить видалити наступним комітом.
Він лишається в історії. Спершу відкличте і замініть секрет, потім чистіть історію.
Гілка в Git — копія всіх файлів проєкту.
Гілка — лише вказівник на коміт, тому створюється миттєво.
Робити git rebase гілки, з якою вже працюють інші.
rebase змінює хеші комітів. Для спільних гілок використовуйте merge.
git reset --hard або push -f на спільній гілці, щоб «прибрати» коміт.
Для опублікованих комітів — git revert: новий коміт, що скасовує зміни, без переписування чужої історії.
git pull і git fetch — одне й те саме.
fetch лише завантажує зміни в локальний репо; pull = fetch + merge у поточну гілку.
Зробив git add — зміни вже на GitHub.
add → індекс, commit → локальний репо, і лише push → сервер.
Комітити .env, ключі, terraform.tfstate.
Додайте їх у .gitignore заздалегідь; секрети зберігайте в Secrets CI-системи.
