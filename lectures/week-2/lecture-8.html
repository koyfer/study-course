Infrastructure as Code і Terraform: HCL, state, init → plan → apply

Інфраструктура як код — це коли сервери, мережі й бази описуються текстовими файлами в Git, а не створюються кліками в консолі. Так інфраструктура стає відтворюваною, перевірюваною і версіонованою.

Чого ви навчитесь#

  • Дати визначення IaC і пояснити, чим він кращий за ручне налаштування.
  • Розрізняти configuration management, server templating і provisioning та назвати інструменти кожного типу.
  • Пояснити ключові поняття Terraform: provider, resource, variable, output, state.
  • Прочитати і написати простий HCL-блок.
  • Знати, що робить кожна команда циклу init → plan → apply → destroy.
  • Порівняти Ansible (agentless, push) з Puppet/Chef (агенти, pull) і пояснити remote state та модулі Terraform.

Що таке Infrastructure as Code#

Визначення

Infrastructure as Code (IaC) — процес управління IT-інфраструктурою, що застосовує найкращі практики DevOps-розробки до хмарних ресурсів. Ресурси організації кодифікуються в текстові файли, які зберігаються в системі контролю версій (Git) — це відкриває feature-гілки, pull request-и і, як наслідок, CI/CD для інфраструктури.

Нагадування з «хмарної піраміди»: що нижче (IaaS), то більше контролю і роботи з інфраструктурою — саме тут працює DevOps і саме тут IaC дає найбільший ефект.

Вручну («ClickOps»)

  • Кроки в консолі ніде не записані
  • Друге середовище відрізняється від першого
  • Відновлення після аварії — з пам'яті
  • Немає рев'ю змін

Як код

  • Файли = документація інфраструктури
  • dev/stage/prod з одного коду — однакові
  • Відтворення за хвилини
  • Зміни проходять pull request і історію Git

Передісторія: спершу інфраструктуру автоматизували скриптами (Bash, Python, Ruby, PowerShell). Потім з'явилися спеціалізовані інструменти: Vagrant, Docker, Terraform, Ansible, Packer. Повна «карта» — CNCF Landscape: Ansible, Chef, Puppet, SaltStack, Pulumi, Terraform та десятки інших.

Три типи IaC-інструментів#

IdempotentІдемпотентність

Повторний запуск дає той самий результат: якщо nginx уже встановлено, вдруге нічого не зміниться.

Immutable infrastructureНезмінна інфраструктура

Сервер не «латають» на місці, а замінюють новим із нового образу. Менше дрейфу конфігурації.

DeclarativeДекларативний підхід

Описуєте бажаний стан («2 ВМ типу e2-small»), а інструмент сам вирішує, що створити, змінити чи видалити. Так працює Terraform.

Чому Terraform#

  • Безкоштовний і з відкритим кодом (HashiCorp), написаний на Go.
  • Простий в установці — один бінарний файл; перевірка: terraform -version.
  • Мультиплатформний: сотні провайдерів — AWS, GCP, Azure, VirtualBox, Docker, Kubernetes… «Керуй будь-чим, що має API».
  • Цілі: уніфікований погляд на ресурси, підтримка IaaS/PaaS/SaaS, безпечні й передбачувані зміни, робочий процес, що не залежить від технології.

Ключові поняття Terraform#

ProviderПровайдер

Плагін, що взаємодіє з API сервісу (hashicorp/aws, hashicorp/google, terra-farm/virtualbox). Завантажується з Terraform Registry.

ResourceРесурс

Блок, що описує один чи кілька об'єктів інфраструктури: ВМ, мережу, DNS-запис, навіть локальний файл.

VariableЗмінна

Пара ключ-значення для налаштування конфігурації без зміни коду.

OutputВихідне значення

Значення, яке модуль повертає (виводить у CLI або передає іншим конфігураціям), напр. IP створеної ВМ.

StateСтан

Закешована інформація про керовану інфраструктуру: зв'язок «ресурс у коді ↔ реальний об'єкт».

Змінні

ВидЯк задається
InputБлок variable; значення передаються до виконання (CLI -var, файл .tfvars, default)
LocalБлок locals — внутрішні обчислені значення, можуть посилатися на інші змінні
OutputБлок output — вивести результат у CLI
EnvironmentЗмінні оточення з префіксом TF_VAR_: export TF_VAR_db_username=admin

Типи значень: string, number (цілі й дробові), bool, list/tuple (["us-west-1a", "us-west-1c"], індекс з 0), map/object ({name = "Mabel", age = 52}), null.

HCL: мова конфігурації#

HCL (HashiCorp Configuration Language) візуально схожа на JSON, але має власні структури. Основна мета — оголошувати ресурси; решта можливостей лише робить це гнучкішим. Три складові: блоки (контейнери з типом і мітками), аргументи (ім'я = значення) і вирази (значення або посилання на інші значення).

# загальний синтаксис
<BLOCK TYPE> "<BLOCK LABEL>" "<BLOCK LABEL>" {
  <IDENTIFIER> = <EXPRESSION>   # argument
}

Приклад: ВМ у Google Cloud (зі слайдів)

terraform {
  required_providers {
    google = { source = "hashicorp/google", version = "3.5.0" }
  }
}

provider "google" {
  credentials = file("my_gcp.json")     # ключ сервісного акаунта — НЕ комітити в Git!
  project     = "project_vasis"
  region      = "europe-north1"
  zone        = "europe-north1-a"
}

resource "google_compute_instance" "vm_instance" {
  name         = "moodle"
  machine_type = "e2-small"
  boot_disk {
    initialize_params { image = "ubuntu-2004-focal-v20210720" }
  }
}

Змінні та виходи (практика з VirtualBox)

variable "type_network" { default = "bridged" }

resource "virtualbox_vm" "node" {
  count  = 2                                     # дві однакові ВМ
  name   = format("node-%02d", count.index + 1)  # node-01, node-02
  image  = "…/ubuntu/boxes/xenial64/…/virtualbox.box"
  cpus   = 2
  memory = "2048 mib"
  network_adapter { type = var.type_network }
}

output "IPAddr" {
  value = element(virtualbox_vm.node.*.network_adapter.0.ipv4_address, 1)
}

На лекції провайдер terra-farm/virtualbox (alpha-версія) збирали з вихідного коду (go build) і запускали terraform apply -parallelism=1, щоб ВМ створювались по черзі. Це дозволяє вчитися IaC локально, без хмарних рахунків.

Життєвий цикл: init → plan → apply → destroy#

КомандаЩо робить
terraform initІніціалізує робочий каталог: завантажує провайдерів. Першою після написання нової конфігурації або клонування з Git
terraform planБудує план: читає поточний стан реальних об'єктів, порівнює конфігурацію з попереднім state, пропонує дії, щоб реальність відповідала коду
terraform applyВиконує план (з підтвердженням yes) і оновлює state
terraform destroyВидаляє всі ресурси, якими керує конфігурація

State

Terraform зберігає стан, щоб зіставляти ресурси з коду з реальними об'єктами, відстежувати метадані і пришвидшувати роботу з великою інфраструктурою. За замовчуванням — локальний файл terraform.tfstate; у команді його зберігають віддалено (наприклад, у S3 чи GCS), щоб усі працювали з одним станом.

Безпека

State і файли облікових даних (як my_gcp.json) можуть містити секрети. Додавайте їх у .gitignore; паролі передавайте через TF_VAR_… або менеджер секретів.

Імперативний vs декларативний, Ansible і ще трохи Terraform#

Імперативний підхід

Описуєте кроки: «встанови nginx, скопіюй конфіг, перезапусти». Приклад — Bash-скрипт.

Декларативний підхід

Описуєте бажаний стан: «має бути 2 ВМ і відкритий порт 80». Інструмент сам рахує різницю. Приклад — Terraform, маніфести Kubernetes.

Ansible, Puppet, Chef

AnsiblePuppet / Chef
Агент на серверахне потрібен (agentless) — підключається по SSHпотрібен агент на кожному вузлі
Модельpush: керуючий вузол надсилає зміниpull: агент періодично тягне конфігурацію з master-сервера
МоваYAML-playbooksPuppet DSL / Ruby
# playbook.yml — запуск: ansible-playbook -i inventory.ini playbook.yml
- hosts: web                    # група серверів з inventory
  become: true                  # sudo
  tasks:
    - name: Install nginx
      apt: { name: nginx, state: present }      # модуль; повтор нічого не змінить
    - name: Start nginx
      service: { name: nginx, state: started, enabled: true }

Inventory — список хостів і груп; модулі (apt, copy, service) ідемпотентні.

Terraform: що ще варто знати

  • Модулі — повторно використовувані набори ресурсів (власні або з Terraform Registry), викликаються блоком module.
  • Значення змінних зручно задавати у файлі terraform.tfvars.
  • Remote state: у команді state зберігають не локально, а в спільному бекенді (AWS S3, GCS, Terraform Cloud) з блокуванням (locking), щоб двоє не застосували зміни одночасно. State може містити секрети — у Git його не комітять.
  • terraform fmt — форматує код, terraform validate — перевіряє синтаксис і логіку конфігурації без звернення до хмари.

Типові помилки#

Одразу terraform apply без plan.
Plan показує, що буде створено (+), змінено (~) і знищено (−). Читайте його завжди — деякі зміни перестворюють ресурс.
Змінити ВМ вручну в консолі, «бо швидше».
З'являється дрейф: код і реальність розходяться, наступний apply поверне або зламає зміни. Усі зміни — через код.
Видалити terraform.tfstate, «бо заважає».
Без state Terraform «забуде» створені ресурси і спробує створити їх заново. State бережуть і зберігають віддалено.
Terraform і Ansible — взаємозамінні.
Terraform — provisioning (створити інфраструктуру), Ansible — configuration management (налаштувати ПЗ на ній). Їх часто використовують разом.
