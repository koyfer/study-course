Infrastructure as Code і Terraform: HCL, state, init → plan → apply

Інфраструктура як код — це коли сервери, мережі й бази описуються текстовими файлами в Git, а не створюються кліками в консолі. Так інфраструктура стає відтворюваною, перевірюваною і версіонованою.

Чого ви навчитесь#

  • Дати визначення IaC і пояснити, чим він кращий за ручне налаштування.
  • Розрізняти configuration management, server templating і provisioning та назвати інструменти кожного типу.
  • Пояснити ключові поняття Terraform: provider, resource, variable, output, state.
  • Прочитати і написати простий HCL-блок.
  • Знати, що робить кожна команда циклу init → plan → apply → destroy.
  • Порівняти Ansible (agentless, push) з Puppet/Chef (агенти, pull) і пояснити remote state та модулі Terraform.
  • Організувати проєкт Terraform (versions, providers, main, variables, outputs, lock-файл) і розгорнути вебсервер в AWS.
  • Використовувати посилання, неявні та явні залежності, count і for_each, data sources, функції, модулі і lifecycle.
  • Читати план (+, ~, -/+, -), налаштувати remote state з блокуванням, імпортувати ресурси, вбудувати Terraform у CI.
  • Писати Ansible inventory і playbook з шаблоном і handler, пояснити ідемпотентність, ролі, Vault.

Що таке Infrastructure as Code#

Визначення

Infrastructure as Code (IaC) — процес управління IT-інфраструктурою, що застосовує найкращі практики DevOps-розробки до хмарних ресурсів. Ресурси організації кодифікуються в текстові файли, які зберігаються в системі контролю версій (Git) — це відкриває feature-гілки, pull request-и і, як наслідок, CI/CD для інфраструктури.

Нагадування з «хмарної піраміди»: що нижче (IaaS), то більше контролю і роботи з інфраструктурою — саме тут працює DevOps і саме тут IaC дає найбільший ефект.

Вручну («ClickOps»)

  • Кроки в консолі ніде не записані
  • Друге середовище відрізняється від першого
  • Відновлення після аварії — з пам'яті
  • Немає рев'ю змін

Як код

  • Файли = документація інфраструктури
  • dev/stage/prod з одного коду — однакові
  • Відтворення за хвилини
  • Зміни проходять pull request і історію Git

Передісторія: спершу інфраструктуру автоматизували скриптами (Bash, Python, Ruby, PowerShell). Потім з'явилися спеціалізовані інструменти: Vagrant, Docker, Terraform, Ansible, Packer. Повна «карта» — CNCF Landscape: Ansible, Chef, Puppet, SaltStack, Pulumi, Terraform та десятки інших.

Три типи IaC-інструментів#

IdempotentІдемпотентність

Повторний запуск дає той самий результат: якщо nginx уже встановлено, вдруге нічого не зміниться.

Immutable infrastructureНезмінна інфраструктура

Сервер не «латають» на місці, а замінюють новим із нового образу. Менше дрейфу конфігурації.

DeclarativeДекларативний підхід

Описуєте бажаний стан («2 ВМ типу e2-small»), а інструмент сам вирішує, що створити, змінити чи видалити. Так працює Terraform.

Чому Terraform#

  • Безкоштовний і з відкритим кодом (HashiCorp), написаний на Go.
  • Простий в установці — один бінарний файл; перевірка: terraform -version.
  • Мультиплатформний: сотні провайдерів — AWS, GCP, Azure, VirtualBox, Docker, Kubernetes… «Керуй будь-чим, що має API».
  • Цілі: уніфікований погляд на ресурси, підтримка IaaS/PaaS/SaaS, безпечні й передбачувані зміни, робочий процес, що не залежить від технології.

Структура проєкту і повний приклад для AWS#

Файли типового проєкту

infra/
├── versions.tf          # блок terraform: версія Terraform, required_providers, backend
├── providers.tf         # налаштування провайдерів (регіон, профіль)
├── main.tf              # ресурси
├── variables.tf         # оголошення вхідних змінних
├── outputs.tf           # вихідні значення
├── terraform.tfvars     # значення змінних (не комітити, якщо є секрети)
├── .terraform.lock.hcl  # зафіксовані версії провайдерів — КОМІТИТИ
├── .terraform/          # завантажені провайдери і модулі — НЕ комітити
└── terraform.tfstate    # локальний state — НЕ комітити (краще remote backend)

Terraform читає усі файли *.tf у каталозі як одну конфігурацію; поділ на файли — лише для зручності. .gitignore для проєкту: .terraform/, *.tfstate, *.tfstate.*, *.tfvars з секретами.

Обмеження версій

terraform {
  required_version = ">= 1.6"
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"      # будь-яка 5.x, але не 6.0 (оператор «песимістичного» обмеження)
    }
  }
}

Повний приклад: вебсервер в AWS

# variables.tf
variable "region" {
  type    = string
  default = "eu-central-1"
}
variable "instance_type" {
  type    = string
  default = "t3.micro"
}
variable "my_ip" {
  type        = string
  description = "Ваша IP для SSH, напр. 203.0.113.7/32"
}

# providers.tf
provider "aws" { region = var.region }

# main.tf
data "aws_ami" "ubuntu" {                         # data source: ЗНАЙТИ існуючий об'єкт, а не створити
  most_recent = true
  owners      = ["099720109477"]                  # Canonical
  filter {
    name   = "name"
    values = ["ubuntu/images/hvm-ssd-gp3/ubuntu-noble-24.04-amd64-server-*"]
  }
}

resource "aws_security_group" "web" {
  name = "web-sg"
  ingress {
    from_port   = 80
    to_port     = 80
    protocol    = "tcp"
    cidr_blocks = ["0.0.0.0/0"]          # HTTP для всіх
  }
  ingress {
    from_port   = 22
    to_port     = 22
    protocol    = "tcp"
    cidr_blocks = [var.my_ip]            # SSH лише з вашої адреси
  }
  egress {
    from_port   = 0
    to_port     = 0
    protocol    = "-1"                   # будь-який протокол назовні
    cidr_blocks = ["0.0.0.0/0"]
  }
}

resource "aws_instance" "web" {
  ami                    = data.aws_ami.ubuntu.id               # посилання на data source
  instance_type          = var.instance_type
  vpc_security_group_ids = [aws_security_group.web.id]          # неявна залежність від SG
  user_data              = <<-EOF
    #!/bin/bash
    apt-get update && apt-get install -y nginx
    echo "Hello from Terraform" > /var/www/html/index.html
  EOF
  tags = { Name = "web-01", Project = "study" }
}

# outputs.tf
output "public_ip" { value = aws_instance.web.public_ip }
output "url"       { value = "http://${aws_instance.web.public_ip}" }

Увага: в одному рядку можна записати блок лише з одним аргументом (provider "aws" { region = var.region }). Кілька аргументів через кому в блоці — синтаксична помилка; кома допустима лише всередині значень-об'єктів, як у tags = { Name = "web-01", Project = "study" }.

terraform init                                   # завантажити провайдер aws
terraform plan -var="my_ip=203.0.113.7/32"       # показати, що буде створено: 2 ресурси
terraform apply -var="my_ip=203.0.113.7/32"      # створити (підтвердити yes)
terraform output url                             # http://3.121.x.x
terraform destroy -var="my_ip=203.0.113.7/32"    # прибрати все після навчання

Terraform сам визначив порядок: спочатку security group, потім ВМ, бо ВМ посилається на aws_security_group.web.id. Таку залежність називають неявною (implicit).

Ключові поняття Terraform#

ProviderПровайдер

Плагін, що взаємодіє з API сервісу (hashicorp/aws, hashicorp/google, terra-farm/virtualbox). Завантажується з Terraform Registry.

ResourceРесурс

Блок, що описує один чи кілька об'єктів інфраструктури: ВМ, мережу, DNS-запис, навіть локальний файл.

VariableЗмінна

Пара ключ-значення для налаштування конфігурації без зміни коду.

OutputВихідне значення

Значення, яке модуль повертає (виводить у CLI або передає іншим конфігураціям), напр. IP створеної ВМ.

StateСтан

Закешована інформація про керовану інфраструктуру: зв'язок «ресурс у коді ↔ реальний об'єкт».

Змінні

ВидЯк задається
InputБлок variable; значення передаються до виконання (CLI -var, файл .tfvars, default)
LocalБлок locals — внутрішні обчислені значення, можуть посилатися на інші змінні
OutputБлок output — вивести результат у CLI
EnvironmentЗмінні оточення з префіксом TF_VAR_: export TF_VAR_db_username=admin

Типи значень: string, number (цілі й дробові), bool, list/tuple (["us-west-1a", "us-west-1c"], індекс з 0), map/object ({name = "Mabel", age = 52}), null.

HCL: мова конфігурації#

HCL (HashiCorp Configuration Language) візуально схожа на JSON, але має власні структури. Основна мета — оголошувати ресурси; решта можливостей лише робить це гнучкішим. Три складові: блоки (контейнери з типом і мітками), аргументи (ім'я = значення) і вирази (значення або посилання на інші значення).

# загальний синтаксис
<BLOCK TYPE> "<BLOCK LABEL>" "<BLOCK LABEL>" {
  <IDENTIFIER> = <EXPRESSION>   # argument
}

Змінні та виходи (практика з VirtualBox)

variable "type_network" { default = "bridged" }

resource "virtualbox_vm" "node" {
  count  = 2                                     # дві однакові ВМ
  name   = format("node-%02d", count.index + 1)  # node-01, node-02
  image  = "…/ubuntu/boxes/xenial64/…/virtualbox.box"

На лекції провайдер terra-farm/virtualbox (alpha-версія) збирали з вихідного коду (go build) і запускали terraform apply -parallelism=1, щоб ВМ створювались по черзі. Це дозволяє вчитися IaC локально, без хмарних рахунків.

Залежності

Terraform будує граф залежностей і створює незалежні ресурси паралельно (за замовчуванням до 10 одночасно, -parallelism=N). Залежність буває неявною — один ресурс посилається на атрибут іншого — і явною через depends_on, коли зв'язок не видно з коду (наприклад, застосунок має стартувати лише після створення політики IAM). Граф можна побачити: terraform graph | dot -Tpng > graph.png.

count і for_each: кілька однакових ресурсів

resource "aws_instance" "web" {
  count         = 3                                   # web[0], web[1], web[2]
  ami           = data.aws_ami.ubuntu.id
  instance_type = "t3.micro"
  tags          = { Name = "web-${count.index + 1}" }
}
output "ips" { value = aws_instance.web[*].public_ip }  # splat: список усіх IP

resource "aws_s3_bucket" "env" {
  for_each = toset(["dev", "staging", "prod"])        # env["dev"], env["staging"], env["prod"]
  bucket   = "myapp-${each.key}-artifacts"
}

Різниця важлива: з count ресурси адресуються за індексом, тож видалення елемента з середини списку зсуває індекси, і Terraform захоче перестворити «зсунуті» ресурси. for_each адресує за ключем, і видалення одного елемента зачіпає лише його.

Data sources

Блок data читає інформацію про об'єкти, якими Terraform не керує або які створено деінде: найновіший образ AMI, існуючу VPC, зони доступності регіону, поточний акаунт. Ресурс (resource) — створює і керує; data source — лише читає.

Корисні функції

file("${path.module}/scripts/init.sh")                 # вміст файла
templatefile("nginx.conf.tftpl", { port = 8080 })     # шаблон з підстановкою
cidrsubnet("10.0.0.0/16", 8, 1)                       # "10.0.1.0/24" — нарізати підмережі
lookup(var.sizes, var.env, "t3.micro")                # значення з map за ключем або default
length(var.zones)                                     # кількість елементів
join(",", ["a", "b"])                                 # "a,b"
merge(local.tags, { Name = "web" })                   # об'єднати map-и

Перевірити вираз без застосування можна в інтерактивній консолі: terraform console → cidrsubnet("10.0.0.0/16", 8, 1).

lifecycle

resource "aws_db_instance" "main" {
  # ...
  lifecycle {
    prevent_destroy       = true          # plan із знищенням цього ресурсу завершиться помилкою
    create_before_destroy = true          # при заміні спершу створити новий, потім видалити старий
    ignore_changes        = [tags]        # не «виправляти» теги, змінені поза Terraform
  }
}

Змінні, середовища і щоденні команди Terraform детально#

Звідки Terraform бере значення змінної: порядок пріоритету

Якщо значення задано в кількох місцях, перемагає те, що стоїть нижче в списку:

  1. default у блоці variable — найнижчий пріоритет.
  2. Змінні оточення TF_VAR_ім'я: export TF_VAR_region=eu-west-1.
  3. Файл terraform.tfvars (і terraform.tfvars.json) — підхоплюється автоматично.
  4. Файли *.auto.tfvars — автоматично, в алфавітному порядку.
  5. Опції -var-file=prod.tfvars і -var="region=us-east-1" у командному рядку — у тому порядку, як записані; найвищий пріоритет.

Якщо значення не задано ніде і немає default, Terraform запитає його інтерактивно (у CI це зупинить конвеєр, тому там значення передають явно).

Типи, перевірки і секрети

variable "env" {
  type        = string
  description = "Середовище: dev, staging або prod"
  validation {
    condition     = contains(["dev", "staging", "prod"], var.env)
    error_message = "env має бути dev, staging або prod."
  }
}

variable "instance" {
  type = object({
    type  = string
    count = number
    disks = list(number)
  })
  default = { type = "t3.micro", count = 1, disks = [20] }
}

variable "db_password" {
  type      = string
  sensitive = true          # не показувати значення в plan і apply
}

output "db_endpoint" {
  value = aws_db_instance.main.endpoint
}
output "db_password" {
  value     = var.db_password
  sensitive = true          # output із секретом мусить бути позначений sensitive
}
sensitive не шифрує state

Позначка лише ховає значення у виводі CLI. У файлі terraform.tfstate пароль лежить відкритим текстом. Тому state зберігають у захищеному backend (S3 з шифруванням і обмеженим доступом), а секрети краще брати з менеджера секретів через data source.

Кілька середовищ: workspaces чи окремі каталоги

Workspaces

  • terraform workspace new staging, terraform workspace select prod
  • той самий код, окремий state для кожного workspace
  • у коді: terraform.workspace == "prod" ? 3 : 1
  • просто, але легко помилково застосувати зміни не в тому workspace; середовища не можуть відрізнятися структурою

Окремі каталоги + модулі

  • envs/dev/main.tf, envs/prod/main.tf викликають спільні модулі з різними параметрами
  • окремий backend і state для кожного
  • видно в Git, що саме відрізняється
  • більше файлів, але безпечніше — популярний вибір для production

Дрейф конфігурації: що бачить Terraform після ручної зміни

Колега в консолі AWS відкрив у Security Group порт 3306 «на хвилинку». Наступний plan покаже:

  # aws_security_group.web will be updated in-place

      ~ ingress = [
          - {
              - cidr_blocks = ["0.0.0.0/0"]
              - from_port   = 3306
              - to_port     = 3306
              - protocol    = "tcp"
            },
            # (2 unchanged elements hidden)
        ]
    }
Plan: 0 to add, 1 to change, 0 to destroy.

Terraform прибере ручну зміну, бо джерело істини — код. Якщо порт справді потрібен, його треба додати в код і провести через PR. Саме тому в командах з IaC ручні зміни в консолі заборонені або дозволені лише для читання.

Provisioners — крайній засіб

resource "aws_instance" "web" {
  # ...
  provisioner "remote-exec" {             # виконати команди на ВМ по SSH після створення
    inline = ["sudo apt-get install -y nginx"]
  }
}

HashiCorp радить уникати provisioners: Terraform не знає, що вони зробили, не може це відстежити і відкотити, а збій посеред скрипта лишає ресурс у «зіпсованому» стані. Краще — user_data (cloud-init), готовий образ, зібраний Packer, або Ansible після Terraform.

Життєвий цикл: init → plan → apply → destroy#

КомандаЩо робить
terraform initІніціалізує робочий каталог: завантажує провайдерів. Першою після написання нової конфігурації або клонування з Git
terraform planБудує план: читає поточний стан реальних об'єктів, порівнює конфігурацію з попереднім state, пропонує дії, щоб реальність відповідала коду
terraform applyВиконує план (з підтвердженням yes) і оновлює state
terraform destroyВидаляє всі ресурси, якими керує конфігурація

State

Terraform зберігає стан, щоб зіставляти ресурси з коду з реальними об'єктами, відстежувати метадані і пришвидшувати роботу з великою інфраструктурою. За замовчуванням — локальний файл terraform.tfstate; у команді його зберігають віддалено (наприклад, у S3 чи GCS), щоб усі працювали з одним станом.

Безпека

State і файли облікових даних (як my_gcp.json) можуть містити секрети. Додавайте їх у .gitignore; паролі передавайте через TF_VAR_… або менеджер секретів.

State, план і робота в команді#

Як читати terraform plan

Terraform will perform the following actions:

  # aws_security_group.web will be created
  + resource "aws_security_group" "web" { ... }        # + створити

  # aws_instance.web will be updated in-place
  ~ resource "aws_instance" "web" {
      ~ instance_type = "t3.micro" -> "t3.small"        # ~ змінити на місці
    }

  # aws_instance.old must be replaced
-/+ resource "aws_instance" "old" {                     # -/+ знищити і створити заново
      ~ ami = "ami-0aaa" -> "ami-0bbb" # forces replacement
    }

  # aws_s3_bucket.tmp will be destroyed
  - resource "aws_s3_bucket" "tmp" { ... }              # - знищити

Plan: 2 to add, 1 to change, 2 to destroy.

Рядки -/+ і must be replaced читайте особливо уважно: деякі атрибути (образ ВМ, ім'я БД) не можна змінити на льоту, і ресурс буде видалено разом з даними. Для CI план зберігають у файл і застосовують саме його: terraform plan -out=tfplan → terraform apply tfplan.

Що таке state і навіщо він

  • Файл terraform.tfstate (JSON) зв'язує ресурси з коду з реальними об'єктами (aws_instance.web ↔ i-0abc123) і зберігає їхні атрибути.
  • Без state Terraform не знає, що вже створено, і спробує створити все заново.
  • Дрейф (drift) — розбіжність між state/кодом і реальністю, коли хтось змінив ресурс вручну в консолі. terraform plan його покаже, terraform apply поверне ресурс до опису в коді.
  • State містить усі атрибути у відкритому вигляді, зокрема паролі БД. Тому — шифроване віддалене сховище з обмеженим доступом, а не Git.

Remote backend з блокуванням

terraform {
  backend "s3" {
    bucket         = "mycompany-tfstate"
    key            = "study/web/terraform.tfstate"
    region         = "eu-central-1"
    encrypt        = true
    dynamodb_table = "terraform-locks"   # блокування: другий apply чекатиме, поки перший завершиться
  }
}

Після зміни backend — terraform init -migrate-state. У нових версіях Terraform блокування можна робити і самим S3 (use_lockfile = true).

Terraform у CI/CD

  1. Pull request зі зміною інфраструктури → CI запускає terraform fmt -check, validate, plan і публікує план у коментарі.
  2. Команда переглядає план, як код-рев'ю.
  3. Після злиття в головну гілку CI виконує apply того самого збереженого плану.
  4. Додатково: сканери безпеки (tfsec, Checkov), «policy as code» (OPA, Sentinel) — заборонити, наприклад, публічні S3-бакети.

Альтернативи Terraform: OpenTofu (відкритий форк Terraform після зміни ліцензії у 2023), AWS CloudFormation (YAML/JSON, лише AWS), Azure Bicep, Pulumi (інфраструктура звичайними мовами: Python, TypeScript, Go).

Імперативний vs декларативний, Ansible і ще трохи Terraform#

Імперативний підхід

Описуєте кроки: «встанови nginx, скопіюй конфіг, перезапусти». Приклад — Bash-скрипт.

Декларативний підхід

Описуєте бажаний стан: «має бути 2 ВМ і відкритий порт 80». Інструмент сам рахує різницю. Приклад — Terraform, маніфести Kubernetes.

Ansible, Puppet, Chef

AnsiblePuppet / Chef
Агент на серверахне потрібен (agentless) — підключається по SSHпотрібен агент на кожному вузлі
Модельpush: керуючий вузол надсилає зміниpull: агент періодично тягне конфігурацію з master-сервера
МоваYAML-playbooksPuppet DSL / Ruby
# playbook.yml — запуск: ansible-playbook -i inventory.ini playbook.yml
- hosts: web                    # група серверів з inventory
  become: true                  # sudo
  tasks:
    - name: Install nginx
      apt: { name: nginx, state: present }      # модуль; повтор нічого не змінить
    - name: Start nginx
      service: { name: nginx, state: started, enabled: true }

Inventory — список хостів і груп; модулі (apt, copy, service) ідемпотентні.

Terraform: що ще варто знати

  • Модулі — повторно використовувані набори ресурсів (власні або з Terraform Registry), викликаються блоком module.
  • Значення змінних зручно задавати у файлі terraform.tfvars.
  • Remote state: у команді state зберігають не локально, а в спільному бекенді (AWS S3, GCS, Terraform Cloud) з блокуванням (locking), щоб двоє не застосували зміни одночасно. State може містити секрети — у Git його не комітять.
  • terraform fmt — форматує код, terraform validate — перевіряє синтаксис і логіку конфігурації без звернення до хмари.

Playbook зі змінними, шаблоном і handler

- name: Configure web servers
  hosts: web
  become: true
  vars:
    app_port: 8080
  tasks:
    - name: Install nginx
      ansible.builtin.apt:
        name: nginx
        state: present
        update_cache: true

    - name: Deploy nginx config from template
      ansible.builtin.template:
        src: templates/site.conf.j2        # Jinja2: усередині {{ app_port }}
        dest: /etc/nginx/sites-available/default
      notify: Reload nginx                 # викликати handler, ЛИШЕ якщо файл змінився

    - name: Ensure nginx is running and enabled
      ansible.builtin.service:
        name: nginx
        state: started
        enabled: true

  handlers:
    - name: Reload nginx
      ansible.builtin.service:
        name: nginx
        state: reloaded

Як працює ідемпотентність

Перший запуск: changed=3 — пакет встановлено, файл записано, nginx перечитав конфіг. Другий запуск без змін у коді: changed=0, усі задачі ok, handler не викликається. Модулі apt, template, service спершу перевіряють поточний стан. А от модулі shell і command ідемпотентності не мають — їм додають умови creates:/when:.

Організація коду

  • Roles — повторно використовувані набори задач, шаблонів, змінних і handler-ів у стандартній структурі (roles/nginx/tasks/main.yml, templates/, handlers/, defaults/). Готові ролі — в Ansible Galaxy.
  • Змінні можна задавати в inventory, у group_vars/web.yml, host_vars/web1.yml, у playbook, з командного рядка (-e). Facts — змінні, які Ansible сам збирає про хост (ОС, IP, пам'ять): {{ ansible_facts['distribution'] }}.
  • Ansible Vault шифрує файли з секретами: ansible-vault create secrets.yml, запуск з --ask-vault-pass.

Terraform + Ansible разом

Типовий розподіл: Terraform створює інфраструктуру (мережу, ВМ, балансувальник, БД) і виводить IP-адреси; Ansible налаштовує ОС і застосунок на цих ВМ. Ще поширеніший сучасний варіант — образ із застосунком (Docker або AMI, зібраний Packer) і Terraform без окремого кроку конфігурації («незмінна інфраструктура», immutable infrastructure): замість оновлення сервера створюють новий з нового образу.

Ansible глибше: модулі, змінні, умови, цикли, ролі, Vault#

Правило: спершу шукайте спеціальний модуль. command: apt-get install -y nginx працює, але Ansible не знає, чи щось змінилося, і щоразу показуватиме changed.

Змінні, факти, умови і цикли в одному playbook

- hosts: web
  become: true
  vars:
    app_user: deploy
    packages: [nginx, git, curl]
  tasks:
    - name: Встановити пакети (цикл)
      package:
        name: "{{ item }}"
        state: present
      loop: "{{ packages }}"

    - name: Лише для Debian/Ubuntu — увімкнути firewall ufw (умова на факті)
      community.general.ufw:
        rule: allow
        port: "80"
      when: ansible_facts['os_family'] == "Debian"

    - name: Перевірити, чи є файл міграцій
      stat:
        path: /opt/app/migrate.sh
      register: migr                      # зберегти результат задачі у змінну

    - name: Запустити міграції, якщо файл є
      command: /opt/app/migrate.sh
      when: migr.stat.exists
      run_once: true                      # лише на одному хості групи
  • Факти (facts) — відомості про хост, які Ansible збирає на початку: ОС, IP, пам'ять. Подивитися: ansible web1 -m setup.
  • register зберігає результат задачі для наступних задач.
  • when — умова виконання задачі; loop — повторення для кожного елемента.
  • Змінні можна задавати в inventory, у group_vars/web.yml, host_vars/web1.yml, у playbook і в командному рядку (-e "app_user=ci" має найвищий пріоритет).

Перевірка без змін: «сухий прогін»

ansible-playbook site.yml --syntax-check          # лише синтаксис
ansible-playbook site.yml --check --diff          # що ЗМІНИЛОСЯ Б, і як саме у файлах
ansible-playbook site.yml --limit web1            # лише на одному хості
ansible-playbook site.yml --tags nginx            # лише задачі з тегом nginx
PLAY RECAP ********************************************************************
web1   : ok=8   changed=2   unreachable=0   failed=0   skipped=1   rescued=0   ignored=0
web2   : ok=8   changed=0   unreachable=0   failed=0   skipped=1   rescued=0   ignored=0

Як читати підсумок: ok — задачі, що виконались успішно (включно зі зміненими), changed — скільки з них реально щось змінили, skipped — пропущені через when. Повторний запуск ідемпотентного playbook має дати changed=0 на всіх хостах.

Mutable vs immutable, push vs pull — підсумок

ПідхідСутьІнструментиРизик
Mutable (змінна) інфраструктурасервер живе роками, зміни застосовують на місціAnsible, Puppet, Chefдрейф конфігурації, «сніжинки»
Immutable (незмінна)нова версія = новий образ і нові сервериPacker, Docker, Terraform + ASG, Kubernetesпотрібна автоматизація збірки образів, стан — поза сервером

Типові помилки#

Кілька аргументів блоку можна записати в один рядок через кому.
В один рядок пишеться блок лише з одним аргументом; кома допустима всередині значень-об'єктів (tags = { a = 1, b = 2 }).
.terraform.lock.hcl треба додати в .gitignore разом з .terraform/.
Lock-файл фіксує версії провайдерів — його комітять. Ігнорують каталог .terraform/ і state-файли.
count і for_each взаємозамінні.
count адресує за індексом: видалення елемента з середини зсуває решту і викликає перестворення. for_each адресує за ключем.
Рядок -/+ у плані — безпечне оновлення.
Це знищення і повторне створення ресурсу. Для БД це означає втрату даних, якщо немає бекапу чи prevent_destroy.
Модуль shell в Ansible ідемпотентний, як і apt.
shell і command виконуються щоразу. Для ідемпотентності — спеціалізовані модулі або умови creates/when.
Одразу terraform apply без plan.
Plan показує, що буде створено (+), змінено (~) і знищено (−). Читайте його завжди — деякі зміни перестворюють ресурс.
Змінити ВМ вручну в консолі, «бо швидше».
З'являється дрейф: код і реальність розходяться, наступний apply поверне або зламає зміни. Усі зміни — через код.
Видалити terraform.tfstate, «бо заважає».
Без state Terraform «забуде» створені ресурси і спробує створити їх заново. State бережуть і зберігають віддалено.
Terraform і Ansible — взаємозамінні.
Terraform — provisioning (створити інфраструктуру), Ansible — configuration management (налаштувати ПЗ на ній). Їх часто використовують разом.
