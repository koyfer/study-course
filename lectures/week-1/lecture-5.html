LAMP і SQL: Apache, Nginx, MySQL, запити, JOIN і транзакції

Класичний стек вебзастосунку і мова, якою з ним розмовляє база даних. Усі SQL-приклади виконуються на одній навчальній схемі, тож можна передбачити й перевірити результат кожного запиту.

Чого ви навчитесь#

  • Пояснити, з чого складається LAMP і чим від нього відрізняється LEMP.
  • Орієнтуватися в конфігурації Apache: httpd.conf, DocumentRoot, <Directory>, <VirtualHost>, модулі.
  • Розуміти, навіщо mod_rewrite, .htaccess і директива AllowOverride.
  • Знайти й прочитати логи Apache (ErrorLog, CustomLog).
  • Відтворити послідовність розгортання PHP-застосунку на CentOS і зробити бекап БД.
  • Розрізняти групи SQL-команд (DDL, DML, DCL) і писати базові запити: SELECT … WHERE з BETWEEN, IN, LIKE, IS NULL, а також GROUP BY і JOIN.
  • Безпечно змінювати конфіг (configtest → reload), порівняти Apache і Nginx, PHP-FPM, налаштувати HTTPS і діагностувати 403/404/500/502.
  • Знати групи SQL (DDL, DML, DQL, DCL, TCL), типи даних і обмеження, створювати таблиці з ключами.
  • Писати SELECT з WHERE (BETWEEN, IN, LIKE, IS NULL), ORDER BY, LIMIT, агрегатами, GROUP BY і HAVING; передбачати результат на прикладі.
  • Розрізняти INNER, LEFT, RIGHT, FULL і CROSS JOIN; писати підзапити, UNION.
  • Розуміти DELETE vs TRUNCATE vs DROP, транзакції й ACID, GRANT/REVOKE, індекси і захист від SQL-ін'єкцій.

Що таке LAMP#

LAMP реалізує 3-рівневу архітектуру з лекції 4: клієнт (браузер) → сервер застосунку (вебсервер) → сервер БД.

Apache HTTP ServerВебсервер

Виріс із NCSA HTTPd (Роб МакКул). Назву пояснюють як «a patchy server» — сервер із латками. За статистикою зі слайдів (2018) — 43% активних сайтів.

MySQLСКБД

Створена MySQL AB (1995), у 2008 куплена Sun, у 2010 разом із Sun — Oracle. Сумісний форк — MariaDB.

PHPСкриптова мова

Расмус Лердорф, 1994. Ключові версії: PHP 5 (2004), PHP 7 (2015), PHP 8 (2020). Популярний фреймворк — Laravel.

Чому LAMP досі вивчають? У чаті лекції було гаряче обговорення «застарілості». Позиція інструктора: стек простий, дає швидкий результат і показує принципи, які потім переносяться на NGINX, Node.js чи Java/Tomcat. Близько третини сайтів працює на WordPress, тобто на LAMP. На практиці часто комбінують Apache + NGINX (NGINX спереду як проксі).

Конфігурація Apache#

Apache налаштовується директивами в текстових файлах. Головний файл — httpd.conf (у CentOS: /etc/httpd/conf/httpd.conf; у Debian/Ubuntu: /etc/apache2/apache2.conf + каталоги sites-enabled, mods-enabled). Типи файлів (MIME) читаються з mime.types (директива TypesConfig). Віртуальні хости і модулі рекомендують виносити в окремі файли.

ДирективаПризначення
DocumentRootКаталог, з якого віддаються файли. Шлях з URL додається до нього: /var/www/html + /shop/index.php
<Directory>Група директив для каталогу, його підкаталогів і файлів
<VirtualHost>Налаштування окремого сайту — кілька доменів на одному сервері
LoadModuleПідключити модуль (кожен модуль має свої директиви)
AllowOverrideЯкі директиви дозволено перевизначати в .htaccess
ErrorLog, CustomLog, LogFormatЖурнал помилок, журнал доступу та його формат
<VirtualHost *:80>
    ServerName shop.example.com
    DocumentRoot /var/www/html/opencart/upload
    <Directory /var/www/html/opencart/upload>
        AllowOverride All          # дозволити .htaccess (потрібно для mod_rewrite)
        Require all granted
    </Directory>
    ErrorLog  /var/log/httpd/shop-error.log
    CustomLog /var/log/httpd/shop-access.log combined
</VirtualHost>

Модулі

Apache має модульну архітектуру: ядро — mod_core, решта підключаються через LoadModule. Часто використовувані: ssl, rewrite, proxy, userdir, headers, php.

  • mod_rewrite — переписує URL «на льоту» за правилами на основі регулярних виразів (PCRE). Може мапити URL на файл, робити редирект або внутрішній проксі-запит. Директиви: RewriteEngine, RewriteRule, RewriteCond, RewriteBase, RewriteMap, RewriteOptions. Саме він робить «гарні» URL типу /product/42 замість index.php?route=product&id=42.
  • mod_proxy — перетворює Apache на проксі/шлюз, підтримує протоколи і алгоритми балансування навантаження.
RewriteEngine On
RewriteCond %{REQUEST_FILENAME} !-f        # якщо такого файла немає…
RewriteRule ^product/([0-9]+)$ index.php?id=$1 [L]   # …передати в PHP

.htaccess і AllowOverride

.htaccess («розподілений конфіг») — файл із директивами в каталозі сайту, що діє на цей каталог і всі вкладені. Потрібен, коли власник сайту не має root-доступу до сервера. Директива AllowOverride визначає, що з нього застосовувати: при None (і AllowOverrideList None) сервер навіть не шукає .htaccess, при All — дозволено все.

Логи

  • Error log (ErrorLog) — найважливіший журнал: помилки запуску, падіння скриптів, відмови в доступі. Першим дивимося сюди.
  • Access log (CustomLog) — кожен оброблений запит: IP, час, метод, URL, код статусу, розмір. Формат задає LogFormat.
tail -f /var/log/httpd/error_log           # стежити за помилками в реальному часі
grep " 500 " /var/log/httpd/access_log     # знайти запити із помилкою сервера

Практика: розгортання OpenCart на CentOS#

На лекції розгортали інтернет-магазин OpenCart 2.x. Послідовність — типова для будь-якого PHP-застосунку.

  1. Підготовка ОС (лише для навчального стенда!). Вимкнути firewalld і SELinux, підключити репозиторій EPEL, за проблем із DNS прописати nameserver 8.8.8.8 у /etc/resolv.conf.
  2. MySQL. Додати репозиторій MySQL, встановити mysql-community-server, увімкнути автозапуск і запустити, знайти тимчасовий пароль у /var/log/mysqld.log, запустити mysql_secure_installation.
  3. Користувач і БД. Створити користувача, видати права, створити БД з кодуванням UTF-8.
  4. Apache + PHP. Встановити httpd і пакети PHP (php-mysql, php-gd, php-mbstring…), увімкнути автозапуск; для mod_rewrite змінити AllowOverride None → All.
  5. Код застосунку. Завантажити архів (wget), розпакувати (unzip), скопіювати в /var/www/html, створити config.php з config-dist.php, віддати файли користувачу apache.
  6. Веб-інсталятор. Відкрити http://IP/opencart/upload/install/, ввести параметри БД; після встановлення видалити каталог install/.
# сервіси керуються через systemctl
systemctl enable --now mysqld          # автозапуск + старт (enable і start в одній команді)
systemctl status mysqld
grep password /var/log/mysqld.log      # тимчасовий пароль root
mysql_secure_installation

yum -y install httpd php php-mysql php-gd php-mbstring php-xml
systemctl enable --now httpd

cp -r opencart /var/www/html/
chmod -R 775 /var/www/html/opencart
chown -R apache:apache /var/www/html/opencart
systemctl restart httpd
CREATE USER 'shop'@'localhost' IDENTIFIED BY 'StrongPass!1';   -- локальний доступ
CREATE USER 'shop'@'%' IDENTIFIED BY 'StrongPass!1';           -- з будь-якого хоста
GRANT ALL ON opencart.* TO 'shop'@'localhost';
CREATE DATABASE opencart CHARACTER SET utf8 COLLATE utf8_bin;
SHOW DATABASES;

'user'@'localhost' і 'user'@'%' — різні облікові записи MySQL: перший підключається лише з цього ж сервера, другий — з будь-якої адреси. На слайдах права видаються як GRANT ALL ON *.* (на всі БД) — для стенда ок, для production давайте права лише на потрібну БД.

Нюанси зі слайдів

Старий OpenCart 2.x не працював з новим механізмом автентифікації MySQL 8 і з режимом sql_mode = 'MYSQL40', тому на лекції користувача переводили на mysql_native_password і правили інсталятор. Це приклад реальної DevOps-роботи: сумісність версій. Також нагадування з чату: репозиторії CentOS 7 закриті, частину пакетів доводиться брати з дзеркал — для нових серверів інструктор радить Ubuntu Server.

Експлуатація вебсервера: перевірка конфігу, Nginx, PHP-FPM, HTTPS, діагностика#

Безпечна зміна конфігурації

sudo apachectl configtest          # або httpd -t / apache2ctl -t: перевірити синтаксис → "Syntax OK"
sudo systemctl reload httpd        # перечитати конфіг без розриву поточних з'єднань
sudo systemctl restart httpd       # повний перезапуск (з розривом)
apachectl -S                       # які віртуальні хости завантажено і з яких файлів
apachectl -M                       # список модулів
# Debian/Ubuntu: a2ensite shop.conf, a2enmod rewrite, a2dismod …, потім reload apache2

Правило: спочатку configtest, потім reload. Помилка в конфігу при restart зупинить сервер і всі сайти на ньому, а reload з помилкою залишить працювати стару конфігурацію.

LEMP = Linux + Nginx («engine-x») + MySQL + PHP. Популярна схема: Nginx на портах 80/443 віддає статику і проксіює запити на Apache або PHP-FPM на локальному порту.

server {
    listen 80;
    server_name shop.example.com;
    root /var/www/shop;
    location / { try_files $uri $uri/ /index.php?$args; }
    location ~ \.php$ {
        include fastcgi_params;
        fastcgi_pass unix:/run/php/php8.3-fpm.sock;     # PHP виконує окремий сервіс php-fpm
        fastcgi_param SCRIPT_FILENAME $document_root$fastcgi_script_name;
    }
}

У CentOS/RHEL окремо пам'ятайте про SELinux: файли сайту мають мати тип httpd_sys_content_t (restorecon -Rv /var/www), а щоб Apache міг підключатися до БД по мережі — setsebool -P httpd_can_network_connect_db 1. На навчальному стенді SELinux вимикали, але на production так не роблять.

Резервні копії БД#

mysqldump --all-databases > dump.sql                 # усі БД
mysqldump -u root -p opencart > opencart.sql         # одна БД
mysql -u root -p opencart < opencart.sql             # відновлення

Зверніть увагу на напрямок перенаправлення з лекції 2: > — вивантажити дамп у файл, < — подати файл на вхід клієнту mysql.

Як робити бекапи правильно

mysqldump --single-transaction --routines --triggers shop | gzip > shop_$(date +%F).sql.gz
# --single-transaction: узгоджений знімок InnoDB без блокування таблиць на час дампу
gunzip < shop_2026-11-07.sql.gz | mysql -u root -p shop    # відновлення зі стисненого дампу
mysqldump -u root -p shop product category > two_tables.sql # лише окремі таблиці
mysqldump --no-data shop > schema.sql                       # лише структура (DDL)
  • Правило 3-2-1: три копії даних, на двох різних носіях, одна — поза основним майданчиком (інший регіон хмари, об'єктне сховище S3).
  • Автоматизуйте: cron або systemd timer + ротація старих копій (скрипт у лекції 3).
  • Перевіряйте відновлення: бекап, з якого жодного разу не відновлювались, — лише надія. Регулярно розгортайте дамп у тестову БД.
  • Не зберігайте пароль у командному рядку (його видно в ps та історії): використовуйте ~/.my.cnf з правами 600.
  • У хмарі для керованих БД (AWS RDS, Cloud SQL) бекапи і point-in-time recovery вмикаються налаштуванням.

SQL: реляційна модель і групи команд#

SQL (Structured Query Language) — декларативна мова роботи з реляційними БД: MySQL/MariaDB, PostgreSQL, MS SQL Server, Oracle, SQLite. «Декларативна» означає, що ви описуєте що отримати, а як саме шукати, вирішує СКБД.

Реляційна модель

Table / relationТаблиця

Набір однотипних записів, напр. product.

Row / record / tupleРядок

Один запис: один товар.

Column / field / attributeСтовпець

Властивість із типом даних: price DECIMAL(10,2).

Primary keyПервинний ключ

Унікально ідентифікує рядок, не може бути NULL. Часто id INT AUTO_INCREMENT.

Foreign keyЗовнішній ключ

Стовпець, що посилається на первинний ключ іншої таблиці; СКБД не дасть послатися на неіснуючий рядок.

NULLВідсутнє значення

«Невідомо / немає». Це не 0 і не порожній рядок.

Групи команд SQL

ГрупаДля чогоКоманди
DDL — Data Definition Languageструктура: БД, таблиці, індекси, представленняCREATE, ALTER, DROP, TRUNCATE, RENAME
DML — Data Manipulation Languageдані в таблицяхINSERT, UPDATE, DELETE (і SELECT у класифікації, де немає окремої DQL)
DQL — Data Query Languageвибірка данихSELECT
DCL — Data Control Languageправа доступуGRANT, REVOKE
TCL — Transaction Control LanguageтранзакціїBEGIN/START TRANSACTION, COMMIT, ROLLBACK, SAVEPOINT

Підручники розходяться, куди віднести SELECT: до DML (класичний поділ на чотири групи) або в окрему DQL. Якщо в тесті є варіант DQL — SELECT відносять туди; якщо ні — до DML. TRUNCATE змінює дані, але належить до DDL: він перестворює таблицю, а не видаляє рядки по одному.

Навчальна схема: магазин

Усі приклади нижче виконуються на цих двох таблицях. Зверніть увагу на «незручні» дані: товар без категорії і категорія без товарів — саме на них видно різницю між JOIN-ами і роботу з NULL.

CREATE DATABASE shop CHARACTER SET utf8mb4;
USE shop;

CREATE TABLE category (
    id   INT PRIMARY KEY,
    name VARCHAR(50) NOT NULL UNIQUE
);

CREATE TABLE product (
    id          INT AUTO_INCREMENT PRIMARY KEY,
    name        VARCHAR(100) NOT NULL,
    price       DECIMAL(10,2) NOT NULL CHECK (price >= 0),
    category_id INT NULL,
    stock       INT NOT NULL DEFAULT 0,
    FOREIGN KEY (category_id) REFERENCES category(id)
);

SELECT і фільтрація WHERE#

Повна структура запиту і порядок виконання

SELECT   [DISTINCT] стовпці, вирази AS псевдонім   -- 5. що показати
FROM     таблиця [JOIN інша ON умова]             -- 1. звідки
WHERE    умова на рядки                           -- 2. фільтр рядків
GROUP BY стовпці                                  -- 3. групування
HAVING   умова на групи                           -- 4. фільтр груп
ORDER BY стовпці [ASC|DESC]                       -- 6. сортування
LIMIT    n [OFFSET m];                            -- 7. обмеження кількості

Записують у такому порядку, а виконується запит у порядку номерів у коментарях. Звідси правило: у WHERE не можна використати псевдонім з SELECT чи агрегатну функцію (вони ще не обчислені), а в ORDER BY — можна.

Базові вибірки

SELECT * FROM product;                                  -- усі стовпці й рядки
SELECT name, price * 0.9 AS sale_price FROM product;    -- вираз з псевдонімом
SELECT DISTINCT category_id FROM product;               -- унікальні значення: 1, 2, 3, 4, NULL
SELECT name, price FROM product ORDER BY price DESC LIMIT 3;
ORDER BY price DESC LIMIT 3

Задача з тесту: що еквівалентне WHERE Id BETWEEN 2 AND 4

Для цілого Id такі самі рядки дадуть: Id >= 2 AND Id <= 4, Id IN (2, 3, 4), Id > 1 AND Id < 5, NOT (Id < 2 OR Id > 4). Не еквівалентні: Id > 2 AND Id < 4 (лише 3), BETWEEN 4 AND 2 (порожньо), Id >= 2 OR Id <= 4 (усі рядки), Id >= 2 AND <= 4 (синтаксична помилка — у другій умові немає стовпця). Записів IN (2..4), IN (2-4) і LIKE 2..4 SQL не знає: 2..4 — синтаксична помилка, а IN (2-4) обчислить вираз 2−4 = −2 і шукатиме Id = -2.

Підступність NULL

Будь-яке порівняння з NULL дає не TRUE і не FALSE, а UNKNOWN, і рядок у результат не потрапляє. Тому:

  • WHERE category_id <> 1 не поверне Laptop Stand — його NULL «не відомо, чи не дорівнює 1». Щоб врахувати: WHERE category_id <> 1 OR category_id IS NULL.
  • NOT IN (1, NULL) не поверне взагалі нічого — класична пастка з підзапитами, що повертають NULL.
  • COALESCE(category_id, 0) підставляє значення замість NULL; у MySQL — також IFNULL().

CASE: умовний вираз

SELECT name,
       CASE WHEN stock = 0   THEN 'немає'
            WHEN stock < 5   THEN 'закінчується'
            ELSE 'є в наявності' END AS availability
FROM product;

GROUP BY збирає рядки з однаковим значенням у групу, і агрегатні функції рахуються для кожної групи окремо. Усі рядки з NULL потрапляють в одну групу. Правило: у SELECT разом з агрегатами можна писати лише стовпці з GROUP BY (MySQL у старих режимах це дозволяв, але повертав випадкове значення).

WHERE vs HAVING

SELECT category_id, COUNT(*) AS cnt
FROM product
WHERE price > 100              -- 1) спершу відкидаємо дешеві товари (рядки)
GROUP BY category_id
HAVING COUNT(*) >= 2;          -- 2) потім залишаємо лише групи з 2+ товарами
-- результат: (1, 2), (2, 2)

WHERE

  • фільтрує рядки
  • виконується до групування
  • агрегатні функції в ньому заборонені: WHERE COUNT(*) > 1 — помилка

HAVING

  • фільтрує групи
  • виконується після GROUP BY
  • умови з агрегатами: HAVING AVG(price) > 500

JOIN, підзапити, UNION#

JOIN з'єднує рядки двох таблиць за умовою, зазвичай «зовнішній ключ = первинний ключ».

INNER JOIN — лише пари, що знайшлися в обох таблицях

SELECT p.name AS product, c.name AS category
FROM product p
INNER JOIN category c ON p.category_id = c.id;    -- слово INNER можна не писати: JOIN = INNER JOIN

6 рядків: Laptop Stand (без категорії) і Monitors (без товарів) відсутні.

LEFT JOIN — усі рядки лівої таблиці

SELECT c.name AS category, p.name AS product
FROM category c
LEFT JOIN product p ON p.category_id = c.id;

Так знаходять «сирітські» записи: категорії без товарів — … LEFT JOIN … WHERE p.id IS NULL.

Інші види

  • RIGHT JOIN — дзеркально: усі рядки правої таблиці. product p RIGHT JOIN category c = category c LEFT JOIN product p.
  • FULL OUTER JOIN — усі рядки обох таблиць (у MySQL немає, емулюють LEFT JOIN … UNION … RIGHT JOIN; у PostgreSQL є).
  • CROSS JOIN — декартів добуток: кожен рядок з кожним (7 × 5 = 35 рядків). Виходить і тоді, коли забули умову ON.
  • Self join — таблиця з'єднується сама з собою (співробітник і його керівник у тій самій таблиці).

Підзапити

-- товари, дорожчі за середню ціну (775): ThinkPad, MacBook, Galaxy, iPhone
SELECT name, price FROM product
WHERE price > (SELECT AVG(price) FROM product);

-- категорії, в яких є хоч один товар на складі
SELECT name FROM category c
WHERE EXISTS (SELECT 1 FROM product p WHERE p.category_id = c.id AND p.stock > 0);

-- товари з категорій, назва яких починається на P або T
SELECT name FROM product
WHERE category_id IN (SELECT id FROM category WHERE name LIKE 'P%' OR name LIKE 'T%');

UNION

UNION об'єднує результати двох запитів з однаковою кількістю й типами стовпців і прибирає дублікати; UNION ALL залишає дублікати (і працює швидше).

SELECT name FROM category
UNION
SELECT name FROM product;      -- спільний список назв

INSERT INTO category (id, name) VALUES (6, 'Cameras');

Транзакції і ACID

Транзакція — група операцій, що виконується як одне ціле: або всі, або жодна. Класичний приклад — переказ грошей: списати з одного рахунку й зарахувати на інший.

START TRANSACTION;
UPDATE account SET balance = balance - 100 WHERE id = 1;
UPDATE account SET balance = balance + 100 WHERE id = 2;
COMMIT;            -- зафіксувати; при помилці замість COMMIT — ROLLBACK (скасувати все)
ВластивістьЗначення
Atomicity — атомарністьусе або нічого
Consistency — узгодженістьпісля транзакції дані відповідають усім правилам (ключі, обмеження)
Isolation — ізоляціяпаралельні транзакції не бачать проміжних станів одна одної
Durability — довговічністьпісля COMMIT дані збережено навіть при збої живлення

У MySQL транзакції підтримує рушій InnoDB (за замовчуванням з версії 5.5); старий MyISAM — ні. За замовчуванням увімкнено autocommit: кожна окрема команда — своя транзакція.

Користувачі та права (DCL)

CREATE USER 'shop_app'@'10.0.1.%' IDENTIFIED BY 'S3cure!pass';   -- вхід лише з підмережі застосунку
GRANT SELECT, INSERT, UPDATE, DELETE ON shop.* TO 'shop_app'@'10.0.1.%';
GRANT ALL PRIVILEGES ON shop.* TO 'admin'@'localhost';
SHOW GRANTS FOR 'shop_app'@'10.0.1.%';
REVOKE DELETE ON shop.* FROM 'shop_app'@'10.0.1.%';
DROP USER 'old_user'@'%';

Принцип найменших привілеїв: застосунку — лише DML на свою БД, без DROP і GRANT; адміністрування — окремим користувачем лише з localhost. Користувач у MySQL — це пара ім'я + хост: 'app'@'localhost' і 'app'@'%' — різні облікові записи.

Індекси

Індекс — додаткова структура (B-дерево), що дозволяє знаходити рядки без перегляду всієї таблиці, як предметний покажчик у книзі. Первинний ключ і UNIQUE індексуються автоматично. Індекси прискорюють WHERE, JOIN, ORDER BY, але сповільнюють запис і займають місце. Чи використовується індекс, показує EXPLAIN SELECT ….

Нормалізація коротко

  • 1NF: у клітинці одне значення (не «Laptops, Phones» в одному полі), рядки унікальні.
  • 2NF: кожен неключовий стовпець залежить від усього первинного ключа.
  • 3NF: неключові стовпці не залежать один від одного (назву категорії зберігаємо в category, а не повторюємо в кожному товарі).

SQL-ін'єкції

Якщо застосунок склеює запит з даних користувача, зловмисник може дописати свій SQL:

// ВРАЗЛИВО: $id = "1 OR 1=1" поверне всі рядки, "1; DROP TABLE product" — гірше
$sql = "SELECT * FROM product WHERE id = " . $_GET['id'];

// ПРАВИЛЬНО: параметризований запит (prepared statement)
$stmt = $pdo->prepare("SELECT * FROM product WHERE id = ?");
$stmt->execute([$_GET['id']]);

Захист: параметризовані запити, мінімальні права користувача БД, WAF. Для DevOps-інженера це ще й аргумент, чому застосунок не повинен підключатися до БД як root.

Типові помилки#

WHERE email = NULL знайде рядки без email.
Порівняння з NULL дає UNKNOWN, тож 0 рядків. Правильно: IS NULL / IS NOT NULL.
BETWEEN 2 AND 4 не включає межі.
Включає обидві: це >= 2 AND <= 4. І менша межа має йти першою.
WHERE COUNT(*) > 1 відфільтрує групи.
Агрегати в WHERE заборонені — фільтр груп пишуть у HAVING після GROUP BY.
TRUNCATE — це DML, як DELETE.
TRUNCATE належить до DDL: швидко перестворює таблицю, без WHERE, скидає AUTO_INCREMENT і не відкочується.
COUNT(column) завжди дорівнює кількості рядків.
COUNT(column) не рахує NULL; кількість рядків — COUNT(*).
Після зміни конфігу Apache — одразу restart.
Спочатку apachectl configtest, потім reload: помилка в конфігу при restart зупинить усі сайти.
WHERE email = NULL знайде записи без email.
З NULL порівнюють лише через IS NULL / IS NOT NULL.
BETWEEN не включає межі, або порядок меж не важливий.
BETWEEN 2 AND 4 включає 2 і 4; нижня межа має бути першою.
Правила .htaccess «не працюють», хоча файл на місці.
Перевірте AllowOverride для каталогу (при None файл ігнорується) і чи завантажено mod_rewrite. Після змін у конфігу — systemctl restart httpd.
Сайт видає 403/500 — одразу chmod -R 777.
Спершу error_log. Зазвичай досить віддати файли користувачу вебсервера (chown -R apache:apache) з правами 755/644.
Вимкнути firewall і SELinux на production, як на лабі.
На production відкривають лише потрібні порти (80/443) і налаштовують SELinux-контексти, а не вимикають захист.
Забути видалити install/ після встановлення CMS.
Каталог інсталятора дозволяє перевстановити сайт і перезаписати БД — його видаляють одразу.
