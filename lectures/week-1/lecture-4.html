Архітектура вебзастосунків: HTTP, REST API, N-tier і мікросервіси

Майже все сучасне ПЗ — вебзастосунки або клієнти вебсервісів. Щоб розгортати й підтримувати їх, треба розуміти, як браузер говорить із сервером і з яких шарів складається система.

Чого ви навчитесь#

  • Описати шлях запиту від введення адреси в браузері до відображення сторінки.
  • Пояснити властивості HTTP (request-response, stateless) і роль cookies.
  • Розрізняти HTTP-методи, GET vs POST у формах, URL vs URI.
  • Порівняти 2-tier, 3-tier і N-tier архітектури, frontend і backend, монолітну та мікросервісну.
  • Спроєктувати REST-ендпоінти для CRUD і викликати їх через curl.
  • Пояснити HTTPS/TLS, різницю між вебсервером і сервером застосунку, роль балансувальника, кешу і CDN.

Клієнт-сервер і веб#

Модель клієнт-сервер розділяє систему на клієнтів і сервери, що спілкуються мережею. Клієнт ініціює сеанс і надсилає запити; сервер чекає запитів від будь-яких клієнтів і відповідає. Мобільні застосунки — теж клієнти: вони звертаються до вебсерверів і вебсервісів.

Вебсайт переважно показує інформацію (контент однаковий для всіх), вебзастосунок — інтерактивний: користувач створює і змінює дані (той самий CRUD з лекції 1).

HypertextГіпертекст

Нелінійний текст із посиланнями на інші тексти (термін Теда Нельсона, ~1965).

HypermediaГіпермедіа

Гіпертекст, що містить не лише текст, а й графіку, відео, звук.

HTTPHyperText Transfer Protocol

Протокол обміну гіпертекстом за схемою «запит — відповідь».

Як працює HTTP-запит#

Властивості HTTP

  • Request-response: транзакцію завжди починає клієнт, сервер генерує відповідь.
  • Ідентифікація ресурсу: кожен запит містить URI.
  • Stateless (без стану): сервер не пам'ятає попередніх запитів — кожен запит незалежний.
  • Метадані: заголовки (headers) передають інформацію про дані — тип вмісту, довжину, кукі, авторизацію.
GET /index.html HTTP/1.1          ← рядок запиту: метод, шлях, версія
Host: shop.com                    ← заголовки
Accept: text/html

HTTP/1.1 200 OK                   ← рядок статусу
Content-Type: text/html; charset=utf-8
Set-Cookie: session=abc123

<html>…</html>                   ← тіло відповіді

Класи кодів статусу: 2xx — успіх (200 OK, 201 Created), 3xx — перенаправлення (301, 302), 4xx — помилка клієнта (400, 401, 403, 404), 5xx — помилка сервера (500, 502, 503).

URL, URI, URN

URI — рядок, що ідентифікує ресурс. URL — підвид URI, що вказує, де ресурс і як до нього дістатися (схема + адреса). URN — ідентифікує ресурс за ім'ям. Кожен URL — це URI, але не кожен URI — URL.

HTTP-методи#

Методи («дієслова») показують, що зробити з ресурсом: GET, POST, PUT, PATCH, DELETE, HEAD, OPTIONS, TRACE, CONNECT. Метод може бути безпечним (не змінює дані), ідемпотентним (повтор дає той самий результат) і кешованим.

МетодДія (CRUD)БезпечнийІдемпотентний
GETRead — отриматитактак
POSTCreate — створитиніні
PUTUpdate — замінити повністюнітак
PATCHUpdate — змінити частину полівніне гарантовано
DELETEDelete — видалитинітак
HEADяк GET, але без тіла відповідітактак

GET vs POST у HTML-формах

Звичайна HTML-форма вміє лише GET і POST. Дані форми завжди передаються як словник ключ=значення (ключ — атрибут name поля), пари з'єднуються через &: view=home&op=translate&sl=en&tl=uk&text=advertisement.

GET

  • Дані в URI (рядок запиту після ?).
  • Обмеження довжини URI (~2048 символів у багатьох браузерах).
  • Видно в адресному рядку, історії, логах → не для паролів.
  • Можна зберегти в закладки.

POST

  • Дані в тілі (body) запиту.
  • Розмір тіла протоколом не обмежений.
  • Не видно в URL (але без HTTPS не зашифровано!).
  • Для створення ресурсів, логіну, завантаження файлів.

Інструктор у чаті наголосив: на практиці найчастіше трапляються GET і POST, але правильний REST-стиль використовує всі базові методи — цього очікують у командах.

Cookies: стан поверх stateless-протоколу#

2-tier, 3-tier, N-tier#

  • 2-tier: клієнт (браузер) ↔ вебсервер (який сам працює і з даними).
  • 3-tier: клієнт ↔ сервер застосунку ↔ окремий сервер БД.
  • N-tier: додаткові рівні — балансувальники навантаження, кілька серверів застосунку, кеші. Масштабується горизонтально.

Класичний вебзастосунок (3-tier): БД зберігає дані, вебсервер містить бізнес-логіку і шар доступу до даних і динамічно генерує HTML. Явного поділу на frontend/backend немає — усе на сервері.

Frontend, backend і AJAX#

Backend (server-side)

Код виконується на сервері під керуванням вебсервера. Мови: Perl, PHP, Python, Java, C#, Ruby, JavaScript (Node.js). БД: Oracle, MS SQL, MySQL, PostgreSQL, DB2, Firebird…

Frontend (client-side)

Код виконується на машині клієнта в браузері: HTML, CSS, JavaScript і фреймворки.

AJAX (Asynchronous JavaScript and XML) — підхід, що дозволив розділити логіку між frontend і backend. Розроблений Microsoft у 1999, назву дав Джессі Джеймс Гаррет у 2005. JavaScript у браузері надсилає запит асинхронно і оновлює частину сторінки без її перезавантаження.

Сьогодні замість XMLHttpRequest використовують fetch або бібліотеки на кшталт axios, а для двостороннього каналу в реальному часі — WebSocket. За словами інструктора, AJAX не застарів — змінилися бібліотеки, а призначення в цих технологій різне.

API і REST#

API (Application Programming Interface) — набір функцій і процедур, через які одна програма отримує доступ до даних і можливостей іншої програми, сервісу чи ОС.

REST (Representational State Transfer) — архітектурний стиль вебсервісів. Кожна одиниця інформації однозначно визначається URL (URL фактично стає «первинним ключем»), а дії задаються HTTP-методами; операції — без стану.

ЗапитЩо робить
GET /book/3отримати книгу №3
GET /book/3/page/35сторінка 35 книги 3 (вкладені ресурси)
POST /bookдодати книгу (дані в тілі)
PUT /book/3замінити книгу 3 (дані в тілі)
PATCH /book/3змінити окремі поля
DELETE /book/3видалити книгу 3

Виклик API через curl

# GET — список ресурсів
curl https://api.example.com/clubs

# POST з JSON-тілом
curl -X POST https://api.example.com/signin \
  -H "Content-Type: application/json" \
  -d '{"email": "test@gmail.com", "password": "user"}'

# запит з токеном авторизації, -i показує заголовки відповіді
curl -i -H "Authorization: Bearer <token>" -X GET https://api.example.com/user/32

Ключі curl: -X — метод, -H — заголовок, -d — тіло, -i — показати заголовки відповіді. Зручно поєднувати з jq для читабельного JSON.

Моноліт vs мікросервіси#

Монолітна архітектура

  • Один застосунок: інтерфейс, логіка і доступ до даних в одній програмі на одній платформі.
  • Просто розробити і розгорнути на старті.
  • Важко масштабувати частинами; одна помилка може покласти все.

Мікросервіси

  • Набір малих незалежних сервісів (користувачі, замовлення, оплата), кожен зі своєю БД, спілкуються через API.
  • Масштабуються і розгортаються окремо.
  • Складніше: мережа, моніторинг, оркестрація → тут і потрібні Docker та CI/CD.

HTTPS, вебсервер і сервер застосунку, балансування, кеш#

HTTPS і TLS

HTTPS — це HTTP поверх TLS (застаріла назва — SSL). Типові порти: HTTP — 80, HTTPS — 443. TLS дає три речі: шифрування трафіку, цілісність (дані не підмінили дорогою) і автентифікацію сервера через сертифікат, підписаний центром сертифікації (CA). Безкоштовні сертифікати видає Let's Encrypt. Під час TLS-рукостискання (handshake) браузер перевіряє сертифікат і узгоджує ключ сеансу; далі дані йдуть зашифровано.

Хто що робить на сервері

РольЩо робитьПриклади
Вебсерверприймає HTTP(S), віддає статику (HTML, CSS, картинки)Apache httpd, NGINX
Сервер застосунку / runtimeвиконує бізнес-логіку (код backend)Tomcat (Java), Gunicorn (Python), Node.js, PHP-FPM
Reverse proxy / балансувальникстоїть перед серверами, завершує TLS, розподіляє запитиNGINX, HAProxy, AWS ELB

Балансування навантаження і масштабування

Балансувальник розподіляє запити між кількома однаковими серверами за алгоритмом: round robin (по черзі), least connections (туди, де менше з'єднань), IP hash (один клієнт — завжди один сервер). Health check прибирає з ротації сервер, що не відповідає. Щоб додавати сервери горизонтально, застосунок має бути stateless: сесії зберігають не в пам'яті сервера, а в спільному сховищі (Redis, БД).

Кешування і CDN

  • Кеш браузера — керується заголовками відповіді (Cache-Control, ETag).
  • CDN (Content Delivery Network: Cloudflare, Amazon CloudFront) — копії статичних файлів на серверах по всьому світу, ближче до користувача: швидше і менше навантаження на ваш сервер.
  • Серверний кеш (Redis, Memcached) — готові результати важких запитів до БД.

Типові помилки#

HTTPS — окремий протокол замість HTTP.
Це той самий HTTP, загорнутий у шифрований канал TLS (порт 443).
POST безпечний, бо дані «сховані».
POST лише не показує дані в URL. Без HTTPS тіло запиту передається відкритим текстом, як і кукі.
Сервер сам пам'ятає, що я залогінений.
HTTP stateless. «Пам'ять» забезпечують cookies/токени, які клієнт надсилає з кожним запитом.
URL і URI — різні непов'язані речі.
URL — підмножина URI: ідентифікатор, що ще й вказує розташування ресурсу.
Видаляти через GET /deleteBook?id=3 — нормально.
Технічно можливо, але порушує семантику: GET має бути безпечним (його кешують, префетчать). Для видалення — DELETE /book/3.
