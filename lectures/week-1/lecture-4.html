Архітектура вебзастосунків: HTTP, REST API, N-tier і мікросервіси

Майже все сучасне ПЗ — вебзастосунки або клієнти вебсервісів. Щоб розгортати й підтримувати їх, треба розуміти, як браузер говорить із сервером і з яких шарів складається система.

Чого ви навчитесь#

  • Описати шлях запиту від введення адреси в браузері до відображення сторінки.
  • Пояснити властивості HTTP (request-response, stateless) і роль cookies.
  • Розрізняти HTTP-методи, GET vs POST у формах, URL vs URI.
  • Порівняти 2-tier, 3-tier і N-tier архітектури, frontend і backend, монолітну та мікросервісну.
  • Спроєктувати REST-ендпоінти для CRUD і викликати їх через curl.
  • Пояснити HTTPS/TLS, різницю між вебсервером і сервером застосунку, роль балансувальника, кешу і CDN.
  • Знати коди статусу HTTP і заголовки, читати вивід curl -v, розрізняти версії HTTP/1.1, 2 і 3.
  • Пояснити сесії і кукі (HttpOnly, Secure, SameSite), Basic, Bearer/JWT, OAuth і CORS.
  • Спроєктувати REST API з правильними методами і кодами відповіді; знати SOAP, GraphQL, gRPC.
  • Порівняти моноліт і мікросервіси, синхронну й асинхронну взаємодію, правила Twelve-Factor.
  • Розрізняти forward і reverse proxy, балансування L4 і L7, описати TLS-рукостискання і ланцюжок сертифікатів.

Клієнт-сервер і веб#

Модель клієнт-сервер розділяє систему на клієнтів і сервери, що спілкуються мережею. Клієнт ініціює сеанс і надсилає запити; сервер чекає запитів від будь-яких клієнтів і відповідає. Мобільні застосунки — теж клієнти: вони звертаються до вебсерверів і вебсервісів.

Вебсайт переважно показує інформацію (контент однаковий для всіх), вебзастосунок — інтерактивний: користувач створює і змінює дані (той самий CRUD з лекції 1).

HypertextГіпертекст

Нелінійний текст із посиланнями на інші тексти (термін Теда Нельсона, ~1965).

HypermediaГіпермедіа

Гіпертекст, що містить не лише текст, а й графіку, відео, звук.

HTTPHyperText Transfer Protocol

Протокол обміну гіпертекстом за схемою «запит — відповідь».

Як працює HTTP-запит#

Властивості HTTP

  • Request-response: транзакцію завжди починає клієнт, сервер генерує відповідь.
  • Ідентифікація ресурсу: кожен запит містить URI.
  • Stateless (без стану): сервер не пам'ятає попередніх запитів — кожен запит незалежний.
  • Метадані: заголовки (headers) передають інформацію про дані — тип вмісту, довжину, кукі, авторизацію.
GET /index.html HTTP/1.1          ← рядок запиту: метод, шлях, версія
Host: shop.com                    ← заголовки
Accept: text/html

HTTP/1.1 200 OK                   ← рядок статусу
Content-Type: text/html; charset=utf-8
Set-Cookie: session=abc123

<html>…</html>                   ← тіло відповіді

Класи кодів статусу: 2xx — успіх (200 OK, 201 Created), 3xx — перенаправлення (301, 302), 4xx — помилка клієнта (400, 401, 403, 404), 5xx — помилка сервера (500, 502, 503).

URL, URI, URN

URI — рядок, що ідентифікує ресурс. URL — підвид URI, що вказує, де ресурс і як до нього дістатися (схема + адреса). URN — ідентифікує ресурс за ім'ям. Кожен URL — це URI, але не кожен URI — URL.

Що відбувається, коли ви вводите адресу в браузері: повний шлях#

Класичне питання співбесіди DevOps-інженера. Відповідь торкається майже всіх тем курсу: DNS, TCP, TLS, HTTP, вебсервер, застосунок, БД, кеш. Розберемо запит https://shop.example.com:443/catalog/phones?sort=price&page=2#reviews.

Крок 1. DNS: ім'я → IP-адреса

  1. Кеш браузера: чи не питали це ім'я нещодавно?
  2. Кеш ОС і файл /etc/hosts (у Windows — C:\Windows\System32\drivers\etc\hosts). Запис 127.0.0.1 shop.example.com у hosts перекриє DNS — так тестують сайт до перенесення домену.
  3. Рекурсивний резолвер — DNS-сервер провайдера або публічний (8.8.8.8, 1.1.1.1). Якщо відповідь є в його кеші — повертає одразу.
  4. Інакше резолвер іде ланцюжком: кореневий сервер (.) → «за .com відповідають ці сервери» → TLD-сервер .com → «за example.com відповідають ns1.example.com…» → авторитетний сервер домену → shop.example.com A 203.0.113.10.
  5. Відповідь кешується на час TTL (наприклад, 300 с). Тому зміни DNS «розходяться» не миттєво.
dig +short shop.example.com          # 203.0.113.10
dig shop.example.com +trace          # показати весь ланцюжок від кореня
nslookup shop.example.com 1.1.1.1    # запитати конкретний DNS-сервер

Крок 2. TCP-з'єднання (тристороннє рукостискання)

Браузер (192.168.1.20:51734)                 Сервер (203.0.113.10:443)
        ──── SYN, seq=1000 ─────────────────────►
        ◄─── SYN-ACK, seq=5000, ack=1001 ────────
        ──── ACK, ack=5001 ──────────────────────►
        з'єднання встановлено (1 RTT ≈ 20–100 мс)

Порт клієнта — випадковий «ефемерний» (49152–65535), порт сервера — 443. Пара «IP:порт клієнта + IP:порт сервера» однозначно визначає з'єднання.

Крок 3. TLS-рукостискання

Браузер надсилає ClientHello з іменем сайту (SNI), сервер відповідає сертифікатом. Браузер перевіряє: сертифікат виданий на shop.example.com, не прострочений, підписаний довіреним центром сертифікації. Сторони домовляються про сеансовий ключ — далі все зашифровано. TLS 1.3 вкладається в 1 RTT.

Крок 4. HTTP-запит

Зверніть увагу: фрагмента #reviews у запиті немає, а кукі браузер додав автоматично.

Крок 5. Сервер обробляє запит

Інтернет ─► балансувальник (TLS-термінація) ─► Nginx (reverse proxy) ─► застосунок (PHP-FPM / Gunicorn / Node)
                                                  │                           │
                                                  └─ /static/* віддає сам     ├─► Redis (кеш, сесії)
                                                                              └─► MySQL/PostgreSQL (дані)
  1. Балансувальник обирає один із серверів (round robin, least connections) і передає запит.
  2. Nginx бачить шлях /catalog/… — це динамічний запит, передає його застосунку (proxy_pass). Запит /static/app.css Nginx віддав би сам із диска.
  3. Застосунок за кукі session знаходить сесію в Redis — знає користувача.
  4. Робить SQL-запит: SELECT … FROM products WHERE category='phones' ORDER BY price LIMIT 20 OFFSET 20.
  5. Генерує HTML (або JSON для фронтенду), повертає Nginx-у, той — клієнту.

Крок 7. Браузер малює сторінку

Розбирає HTML у дерево DOM, бачить посилання на CSS, JavaScript і картинки — і для кожного робить окремі запити (з кешу, з CDN або з сервера). Сторінка інтернет-магазину легко викликає 50–100 запитів. JavaScript може потім надсилати запити до API (fetch('/api/v1/cart')) без перезавантаження сторінки — це AJAX.

Нарешті браузер прокручує сторінку до елемента з id="reviews" — ось де використовується фрагмент.

Скільки часу займає кожен етап: curl покаже

curl -o /dev/null -s -w 'dns:%{time_namelookup} tcp:%{time_connect} tls:%{time_appconnect} ttfb:%{time_starttransfer} total:%{time_total}\n' https://example.com/
# dns:0.012 tcp:0.045 tls:0.098 ttfb:0.231 total:0.236
МетрикаЩо означаєЯкщо велика — шукайте
time_namelookupDNSповільний резолвер, низький TTL
time_connectдо кінця TCP-рукостисканнявідстань до сервера, перевантажена мережа
time_appconnectдо кінця TLSдовгий ланцюжок сертифікатів, старий TLS
time_starttransfer (TTFB)до першого байта відповідіповільний застосунок або БД — найчастіша причина
time_totalусе разомвеликий розмір відповіді, немає стиснення

Числа накопичувальні: TLS тут зайняв 0,098 − 0,045 = 53 мс, а сервер думав 0,231 − 0,098 = 133 мс.

HTTP-методи#

Методи («дієслова») показують, що зробити з ресурсом: GET, POST, PUT, PATCH, DELETE, HEAD, OPTIONS, TRACE, CONNECT. Метод може бути безпечним (не змінює дані), ідемпотентним (повтор дає той самий результат) і кешованим.

GET vs POST у HTML-формах

Звичайна HTML-форма вміє лише GET і POST. Дані форми завжди передаються як словник ключ=значення (ключ — атрибут name поля), пари з'єднуються через &: view=home&op=translate&sl=en&tl=uk&text=advertisement.

GET

  • Дані в URI (рядок запиту після ?).
  • Обмеження довжини URI (~2048 символів у багатьох браузерах).
  • Видно в адресному рядку, історії, логах → не для паролів.
  • Можна зберегти в закладки.

POST

  • Дані в тілі (body) запиту.
  • Розмір тіла протоколом не обмежений.
  • Не видно в URL (але без HTTPS не зашифровано!).
  • Для створення ресурсів, логіну, завантаження файлів.

Інструктор у чаті наголосив: на практиці найчастіше трапляються GET і POST, але правильний REST-стиль використовує всі базові методи — цього очікують у командах.

Cookies: стан поверх stateless-протоколу#

Сесії, автентифікація і CORS#

Як stateless-протокол «пам'ятає» користувача

  1. Користувач надсилає логін і пароль (POST /login).
  2. Сервер перевіряє їх, створює сесію (запис у Redis або БД з ID сесії) і відповідає Set-Cookie: session=9f2c…; HttpOnly; Secure; SameSite=Lax.
  3. Браузер автоматично додає Cookie: session=9f2c… до кожного наступного запиту на цей домен.
  4. Сервер за ID знаходить сесію і знає, хто це. Вихід — сесію видаляють.
Атрибут cookieЗначення
Expires / Max-Ageстрок життя; без них — «сесійна» кукі до закриття браузера
HttpOnlyJavaScript не бачить кукі — захист від крадіжки через XSS
Secureпередається лише по HTTPS
SameSite=Lax|Strict|Noneчи надсилати кукі з запитами з інших сайтів — захист від CSRF

CORS

Браузер за замовчуванням не дає JavaScript зі сторінки https://app.example.com читати відповіді API з іншого походження (origin = схема + хост + порт), наприклад https://api.example.com. CORS (Cross-Origin Resource Sharing) — механізм, яким сервер API дозволяє це заголовком Access-Control-Allow-Origin: https://app.example.com. Для «складних» запитів (PUT, DELETE, власні заголовки) браузер спершу надсилає попередній запит OPTIONS (preflight). Помилка CORS видна лише в браузері: curl її не відтворить, бо CORS — правило браузера, а не сервера.

2-tier, 3-tier, N-tier#

  • 2-tier: клієнт (браузер) ↔ вебсервер (який сам працює і з даними).
  • 3-tier: клієнт ↔ сервер застосунку ↔ окремий сервер БД.
  • N-tier: додаткові рівні — балансувальники навантаження, кілька серверів застосунку, кеші. Масштабується горизонтально.

Класичний вебзастосунок (3-tier): БД зберігає дані, вебсервер містить бізнес-логіку і шар доступу до даних і динамічно генерує HTML. Явного поділу на frontend/backend немає — усе на сервері.

Frontend, backend і AJAX#

Backend (server-side)

Код виконується на сервері під керуванням вебсервера. Мови: Perl, PHP, Python, Java, C#, Ruby, JavaScript (Node.js). БД: Oracle, MS SQL, MySQL, PostgreSQL, DB2, Firebird…

Frontend (client-side)

Код виконується на машині клієнта в браузері: HTML, CSS, JavaScript і фреймворки.

AJAX (Asynchronous JavaScript and XML) — підхід, що дозволив розділити логіку між frontend і backend. Розроблений Microsoft у 1999, назву дав Джессі Джеймс Гаррет у 2005. JavaScript у браузері надсилає запит асинхронно і оновлює частину сторінки без її перезавантаження.

Сьогодні замість XMLHttpRequest використовують fetch або бібліотеки на кшталт axios, а для двостороннього каналу в реальному часі — WebSocket. За словами інструктора, AJAX не застарів — змінилися бібліотеки, а призначення в цих технологій різне.

API і REST#

API (Application Programming Interface) — набір функцій і процедур, через які одна програма отримує доступ до даних і можливостей іншої програми, сервісу чи ОС.

REST (Representational State Transfer) — архітектурний стиль вебсервісів. Кожна одиниця інформації однозначно визначається URL (URL фактично стає «первинним ключем»), а дії задаються HTTP-методами; операції — без стану.

Виклик API через curl

Ідемпотентність на практиці

Мережа ненадійна: клієнт може не отримати відповідь і повторити запит. Повторний PUT /products/42 із тими самими даними дає той самий стан — безпечно. Повторний POST /orders створить друге замовлення — тому платіжні API приймають заголовок Idempotency-Key, щоб розпізнати повтор. DELETE ідемпотентний за станом: після першого виклику ресурсу немає, і після другого теж (хоча код відповіді може бути 404).

Моноліт vs мікросервіси#

Монолітна архітектура

  • Один застосунок: інтерфейс, логіка і доступ до даних в одній програмі на одній платформі.
  • Просто розробити і розгорнути на старті.
  • Важко масштабувати частинами; одна помилка може покласти все.

Мікросервіси

  • Набір малих незалежних сервісів (користувачі, замовлення, оплата), кожен зі своєю БД, спілкуються через API.
  • Масштабуються і розгортаються окремо.
  • Складніше: мережа, моніторинг, оркестрація → тут і потрібні Docker та CI/CD.

Розгортанняувесь застосунок разомкожен сервіс незалежно, багато разів на день

Як сервіси спілкуються

  • Синхронно: REST або gRPC — сервіс чекає відповіді. Просто, але ланцюжок викликів падає, якщо падає будь-яка ланка.
  • Асинхронно: через брокер повідомлень (RabbitMQ, Apache Kafka, AWS SQS) — сервіс публікує подію «замовлення створено», інші обробляють, коли зможуть. Сервіси слабше зв'язані, піки навантаження згладжуються.
  • API Gateway — єдина точка входу для клієнтів: маршрутизація до сервісів, автентифікація, rate limiting (Kong, AWS API Gateway, Nginx).
  • Service discovery — сервіси знаходять один одного за іменем, а не фіксованою IP (DNS у Kubernetes, Consul).

Twelve-Factor App: як писати застосунки для хмари

Набір правил від Heroku, на яких тримаються контейнери і PaaS. Найважливіші для DevOps:

  1. Одна кодова база в Git — багато розгортань (dev, staging, prod).
  2. Залежності оголошені явно (requirements.txt, package.json), нічого не береться «з системи».
  3. Конфігурація — у змінних середовища, а не в коді (паролі БД, адреси сервісів).
  4. Зовнішні служби (БД, черга, кеш) — підключувані ресурси за URL.
  5. Build, release, run — суворо розділені етапи.
  6. Процеси без стану (stateless); стан — у БД або кеші.
  7. Логи — потік у stdout, а збирає їх середовище виконання.
  8. Dev/prod parity — середовища якомога схожі.

HTTPS, вебсервер і сервер застосунку, балансування, кеш#

HTTPS і TLS

HTTPS — це HTTP поверх TLS (застаріла назва — SSL). Типові порти: HTTP — 80, HTTPS — 443. TLS дає три речі: шифрування трафіку, цілісність (дані не підмінили дорогою) і автентифікацію сервера через сертифікат, підписаний центром сертифікації (CA). Безкоштовні сертифікати видає Let's Encrypt. Під час TLS-рукостискання (handshake) браузер перевіряє сертифікат і узгоджує ключ сеансу; далі дані йдуть зашифровано.

Хто що робить на сервері

РольЩо робитьПриклади
Вебсерверприймає HTTP(S), віддає статику (HTML, CSS, картинки)Apache httpd, NGINX
Сервер застосунку / runtimeвиконує бізнес-логіку (код backend)Tomcat (Java), Gunicorn (Python), Node.js, PHP-FPM
Reverse proxy / балансувальникстоїть перед серверами, завершує TLS, розподіляє запитиNGINX, HAProxy, AWS ELB

Балансування навантаження і масштабування

Балансувальник розподіляє запити між кількома однаковими серверами за алгоритмом: round robin (по черзі), least connections (туди, де менше з'єднань), IP hash (один клієнт — завжди один сервер). Health check прибирає з ротації сервер, що не відповідає. Щоб додавати сервери горизонтально, застосунок має бути stateless: сесії зберігають не в пам'яті сервера, а в спільному сховищі (Redis, БД).

Кешування і CDN

  • Кеш браузера — керується заголовками відповіді (Cache-Control, ETag).
  • CDN (Content Delivery Network: Cloudflare, Amazon CloudFront) — копії статичних файлів на серверах по всьому світу, ближче до користувача: швидше і менше навантаження на ваш сервер.
  • Серверний кеш (Redis, Memcached) — готові результати важких запитів до БД.

Проксі, балансування L4/L7 і TLS детально#

Forward proxy

  • стоїть біля клієнтів і ходить в інтернет від їхнього імені
  • фільтрація, кешування, приховування клієнтів
  • корпоративний проксі, Squid

Reverse proxy

  • стоїть перед серверами і приймає запити від імені сервісу
  • TLS-термінація, балансування, кеш, захист бекендів
  • Nginx, HAProxy, Traefik, Cloudflare
Балансування L4 (транспортне)Балансування L7 (прикладне)
На що дивитьсяIP і порт (TCP/UDP)вміст HTTP: шлях, заголовки, кукі
Можливостідуже швидко, будь-який TCP-протокол (БД, SMTP)маршрутизація /api → API-сервіс, /static → CDN; TLS-термінація, переписування заголовків
ПрикладиAWS Network Load Balancer, HAProxy у режимі tcpAWS Application Load Balancer, Nginx, Traefik

Sticky sessions (прив'язка сесії) — балансувальник відправляє клієнта завжди на той самий сервер (за кукі або IP). Це милиця для застосунків, що тримають сесію в пам'яті; краще зробити застосунок stateless.

TLS-рукостискання (TLS 1.3, спрощено)

  1. ClientHello: клієнт називає підтримувані версії й шифри, ім'я сайту (SNI) і свою частину обміну ключами.
  2. ServerHello + сертифікат: сервер обирає шифр, надсилає свою частину обміну ключами і сертифікат.
  3. Клієнт перевіряє сертифікат: підпис довіреного центру сертифікації (CA), ім'я домену, строк дії, чи не відкликано.
  4. Обидві сторони обчислюють спільний сеансовий ключ (алгоритм Діффі–Геллмана); далі дані шифруються швидким симетричним шифром (AES, ChaCha20).

Ланцюжок довіри: сертифікат сайту підписаний проміжним CA, той — кореневим CA, який вбудовано в ОС або браузер. Якщо сервер не віддає проміжний сертифікат, частина клієнтів побачить помилку. Перевірити: openssl s_client -connect example.com:443 -servername example.com; строк дії: … | openssl x509 -noout -dates.

TLS-термінація на балансувальнику: шифрування знімається на вході, а до бекендів трафік іде по внутрішній мережі (іноді знову шифрується — end-to-end TLS). Так сертифікат зберігається в одному місці, а не на кожному сервері.

Nginx на практиці: статика, reverse proxy, балансування#

Більшість теорії цієї лекції в реальному житті перетворюється на кілька десятків рядків конфігурації Nginx. Ось повний робочий приклад для інтернет-магазину з двома серверами застосунку.

# /etc/nginx/conf.d/shop.conf
upstream shop_app {                       # група бекендів для балансування
    least_conn;                           # алгоритм: туди, де менше активних з'єднань (за замовч. round robin)
    server 10.0.1.11:8000 max_fails=3 fail_timeout=30s;
    server 10.0.1.12:8000 max_fails=3 fail_timeout=30s;
    server 10.0.1.13:8000 backup;         # отримує трафік, лише коли основні недоступні
}

server {                                  # HTTP → HTTPS
    listen 80;
    server_name shop.example.com;
    return 301 https://$host$request_uri; # постійний редирект зі збереженням шляху
}

server {
    listen 443 ssl http2;
    server_name shop.example.com;         # за заголовком Host обирається цей server-блок
    ssl_certificate     /etc/letsencrypt/live/shop.example.com/fullchain.pem;  # сертифікат + проміжні CA
    ssl_certificate_key /etc/letsencrypt/live/shop.example.com/privkey.pem;
    add_header Strict-Transport-Security "max-age=31536000" always;           # HSTS

    location /static/ {                   # статику віддає сам Nginx
        root /var/www/shop;               # /static/app.css → /var/www/shop/static/app.css
        expires 30d;                      # Cache-Control: max-age=2592000
        access_log off;
    }

    location /api/ {                      # API — на бекенди
        proxy_pass http://shop_app;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;   # справжня IP клієнта
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_read_timeout 30s;           # довше — і клієнт отримає 504
    }

    location / {
        proxy_pass http://shop_app;
        proxy_set_header Host $host;
    }
}
sudo nginx -t                    # перевірити синтаксис — ЗАВЖДИ перед reload
sudo systemctl reload nginx      # застосувати без розриву з'єднань (restart розриває)
curl -I http://shop.example.com/            # HTTP/1.1 301 Moved Permanently, Location: https://…
curl -sI https://shop.example.com/static/app.css | grep -i cache   # Cache-Control: max-age=2592000

Алгоритми балансування

АлгоритмЯк обирає серверКоли доречний
Round robinпо черзі: 1, 2, 3, 1, 2, 3…однакові сервери, короткі однакові запити
Weighted round robinпропорційно вазі: сервер з weight=3 отримує втричі більшесервери різної потужності
Least connectionsтуди, де найменше активних з'єднаньзапити різної тривалості (звіти, завантаження файлів)

Health checks: балансувальник періодично перевіряє бекенди (наприклад, GET /health має повернути 200) і виключає «хворі» з ротації. У прикладі вище Nginx робить це пасивно: після 3 помилок поспіль сервер виключається на 30 с.

Кешування HTTP детально#

Заголовок Cache-Control

ДирективаЗначенняПриклад використання
max-age=Nвідповідь свіжа N секунд, можна брати з кешу без запитуCSS/JS/картинки: max-age=31536000 (рік)
no-cacheзберігати можна, але перед використанням перевірити на серверіHTML-сторінки, що змінюються
no-storeне зберігати взагалісторінки з особистими даними, банківські виписки
publicможуть кешувати і проміжні кеші (CDN, проксі)публічна статика
privateкешувати лише браузеру користувачасторінка «мій кабінет»
immutableфайл ніколи не зміниться — навіть не перевірятиapp.3f9a1c.js з хешем у назві
s-maxage=Nокремий строк для спільних кешів (CDN)CDN кешує 10 хв, браузер — 1 хв

Пастка: no-cache не означає «не кешувати» — це означає «кешувати, але щоразу перевіряти». «Не кешувати зовсім» — no-store.

Умовні запити: ETag і 304

── перший запит ──────────────────────────────
GET /static/logo.png
◄ 200 OK
  ETag: "a1b2c3"
  Cache-Control: no-cache
  (тіло 48 КБ)

── повторний запит ───────────────────────────
GET /static/logo.png
If-None-Match: "a1b2c3"          ← «у мене є версія a1b2c3, вона ще актуальна?»
◄ 304 Not Modified               ← «так», тіло НЕ передається, браузер бере з кешу
  (0 байт тіла)

Аналогічно працює пара Last-Modified / If-Modified-Since — з датою замість відбитка.

Стратегія «хеш у назві файла» (cache busting)

Збирач фронтенду (webpack, Vite) кладе хеш вмісту в ім'я: app.3f9a1c.js. Такий файл можна кешувати на рік з immutable: якщо код зміниться, зміниться і ім'я, а HTML (з коротким кешем) уже посилатиметься на app.7b2e40.js. Користувачі отримують нову версію одразу, без «почистіть кеш браузера».

Шпаргалка curl для DevOps#

curl https://api.example.com/products                     # GET, тіло відповіді на екран
curl -i URL                                               # + заголовки відповіді
curl -I URL                                               # лише заголовки (метод HEAD)
curl -v URL                                               # повний обмін: DNS, TLS, заголовки запиту і відповіді
curl -L URL                                               # іти за редиректами 301/302
curl -s -o /dev/null -w '%{http_code}\n' URL              # лише код статусу — для скриптів
curl -f URL                                               # код виходу ≠ 0 при HTTP 4xx/5xx
curl -X POST -H 'Content-Type: application/json' -d '{"name":"x"}' URL   # POST з JSON
curl -X PUT -d @product.json -H 'Content-Type: application/json' URL/42 # тіло з файла
curl -X DELETE URL/42                                     # видалення
curl -u admin:secret URL                                  # Basic Auth
curl -H 'Authorization: Bearer eyJ…' URL                  # токен
curl -b 'session=abc' -c cookies.txt URL                  # надіслати кукі / зберегти отримані
curl -F 'file=@report.pdf' URL/upload                     # завантаження файла (multipart/form-data)
curl --resolve shop.example.com:443:10.0.1.11 https://shop.example.com/   # звернутись до конкретного сервера в обхід DNS
curl -k https://10.0.1.11/                                # ігнорувати помилку сертифіката (лише для діагностики!)
curl -m 5 URL                                             # таймаут 5 секунд
curl -s URL | jq '.items[0].name'                         # витягти поле з JSON

Типові помилки#

401 і 403 — одне й те саме.
401 — не автентифіковано (хто ви?), 403 — автентифіковано, але немає прав.
Basic Auth шифрує пароль.
Base64 — лише кодування, його декодує будь-хто. Basic Auth безпечний тільки поверх HTTPS.
POST ідемпотентний, бо «просто надсилає дані».
Повторний POST зазвичай створює ще один ресурс. Ідемпотентні GET, PUT, DELETE, HEAD.
Помилку CORS можна відтворити через curl.
CORS — правило браузера. curl отримає відповідь, а браузер не дасть JavaScript її прочитати без заголовка Access-Control-Allow-Origin.
HTTPS — окремий протокол замість HTTP.
Це той самий HTTP, загорнутий у шифрований канал TLS (порт 443).
POST безпечний, бо дані «сховані».
POST лише не показує дані в URL. Без HTTPS тіло запиту передається відкритим текстом, як і кукі.
Сервер сам пам'ятає, що я залогінений.
HTTP stateless. «Пам'ять» забезпечують cookies/токени, які клієнт надсилає з кожним запитом.
URL і URI — різні непов'язані речі.
URL — підмножина URI: ідентифікатор, що ще й вказує розташування ресурсу.
Видаляти через GET /deleteBook?id=3 — нормально.
Технічно можливо, але порушує семантику: GET має бути безпечним (його кешують, префетчать). Для видалення — DELETE /book/3.
